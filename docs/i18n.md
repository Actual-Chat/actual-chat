# Localization (i18n)

Voxt ships its UI in **22 languages**. This document is the complete set of
rules for adding, translating and consuming user-visible text.

> The one rule: **never hardcode user-visible English text in UI code.**
> Everything else here is either a mechanism that supports that rule or a
> deliberate, enumerated exception to it.

The supported languages are declared in one place — `Languages.AllUI`
(`src/dotnet/Api/Identifiers/Languages.cs`):

| | | | |
|---|---|---|---|
| English (default) | Español | Français | Italiano |
| Русский | Deutsch | 中文 | हिन्दी |
| 日本語 | 한국어 | Português | Türkçe |
| Українська | Tiếng Việt | Polski | Bahasa Indonesia |
| Čeština | Български | Bosanski | Hrvatski |
| Crnogorski | Српски | | |

A language can be usable for the UI, for transcription, or both — `Language.Support`
carries a `LanguageSupport` flag, and `Languages` exposes the two sets separately:

- **`Languages.AllUI`** — ships a catalog, so the app can render in it. Declared as an
  ordered array because that order is what the App-language picker shows;
  `LanguageSupportTest` keeps it in agreement with the flag.
- **`Languages.AllTranscription`** — offered as a spoken language and accepted by a
  transcriber. Derived from the flag.
- **`Languages.All`** — the union, and what `Language.Parse` resolves against.

The two sets are not the same. Montenegrin ships a UI catalog but no transcriber knows
its `cnr` code, so it is `LanguageSupport.UI` only and never reaches the spoken-language
picker. Most declared languages are the other way round: transcription-only.

Only the **canonical variant** of an `IsoCode` carries `LanguageSupport.UI` — `en-GB`,
`en-IN`, `zh-TW`, `fr-CA`, `pt-BR` and the Spanish variants all resolve to a catalog
their base language already owns.

For what is still *unlocalized* and in what order it will be picked up, see
[the localization plan](./plans/localization-remaining.md). That doc tracks
remaining work; this one carries the rules.

## How the catalog works

Two embedded JSON catalogs per language live in
`src/dotnet/UI.Blazor/Resources/`:

- **`Strings.<iso>.json`** — ordinary UI text, addressed by key. 1252 keys.
- **`Messages.<iso>.json`** — server errors and validation messages, reverse-indexed
  by `MessageIndex` so an English message produced at runtime can be matched back
  to its key. 103 keys.

A key belongs to **exactly one** catalog: `AppStringLocalizer` merges both into a
single forward lookup, so a shared key would make one silently shadow the other.
`AppLocalizationTest.CatalogsShouldNotShareKeys` enforces this.

Both files are **JSONC** — `//` comments and trailing commas are allowed, and the
catalogs use blank lines and comments to group related keys. Keep a new key next
to its group rather than appending it at the end.

Lookup is `AppStringLocalizer` (`src/dotnet/UI.Blazor.App/Services/`), a custom
`IStringLocalizer<Strings>`. The standard `.resx` / `CultureInfo` machinery does
**not** work here: the app runs under `InvariantGlobalization`, which is also why
month and day names come from `Date_*` catalog keys via
`DateFormatsLocalizerExt` rather than from ICU.

**Missing keys never throw.** `GetString` falls back to English, and then to the
key name itself with `resourceNotFound: true`. A key rendered as
`Settings_Something` on screen means the key is absent from every catalog.

## Adding a key

Three edits, all enforced by `AppLocalizationTest`:

1. Add it to `Strings.en.json` **and every other shipped `Strings.*.json`**. All 22
   must define exactly the English key set — no more, no less. Four of them are
   generated — see [Derived catalogs](#derived-catalogs-bcms).
2. Add the matching typed member to
   `src/dotnet/UI.Blazor/Resources/LocalizedStringsLocalizerExt.cs`. One member per
   key, names matching exactly.
3. Use it from code (see [Consuming strings](#consuming-strings)).

### Key naming

`Group_Name` in PascalCase, where the group mirrors the component, page or
feature: `ChatMenu_Pin`, `Settings_Title`, `ErrorToast_ActionFailed`. A one-off
group for a single component is fine and common (`Reconnect_`, `Redirect_`,
`ServerInstance_`).

Format strings get a **`_Format` suffix** and `{0}`-style placeholders. Every
translation must keep every placeholder the English value has —
`EveryShippedTranslationShouldMatchEnglishKeys` checks this per key, and
`EveryLocalizerExtMemberResolvesInEveryLanguage` additionally invokes each member
and fails if the resolved value drops an argument.

## Consuming strings

Always go through the typed members in `LocalizedStringsLocalizerExt`
(`@L.ChatMenu_Pin`, `L.Settings_Quit_Format(appName)`), **never** the raw
`L["..."]` indexer — the typed members make a typo a compile error, and
`LocalizerExtMembersMatchEnglishKeysExactly` keeps members and keys in
one-to-one correspondence.

### Components

Use the `L` property that the `UIHub` base classes already expose. **If a
component has no such base, give it one — do NOT add `[Inject] private
IStringLocalizer L`.** Every base in `src/dotnet/UI.Blazor/BaseTypes/` exposes `L`
(plus `Hub` and the usual service shortcuts), so pick the one matching what the
component already does:

| Component currently | Change `@inherits` to |
|---|---|
| plain `ComponentBase` / no `@inherits` | `ComponentBase<UIHub>` |
| `FusionComponentBase` | `FusionComponentBase<UIHub>` |
| `ComputedStateComponent<TState>` | `ComputedStateComponent<UIHub, TState>` |
| `ComputedRenderStateComponent<TState>` | `ComputedRenderStateComponent<UIHub, TState>` |

In `UI.Blazor.App` use `AppUIHub` instead of `UIHub`. Swapping the base is a
one-line change and costs nothing at runtime — `L` is just `Hub.StringLocalizer`.

**When no wrapper fits** (the component is stuck on a framework or Fusion base),
do *not* write a new `<THub, …>` wrapper for a single consumer — each wrapper
re-declares ~20 shortcut properties, so one is only worth it once several
components share the base. Instead:

- If the base derives from `CircuitHubComponentBase`, the hub is **already
  injected** — just type it, the same way `ComputedStateComponent<THub, TState>`
  does internally. Two lines, no new type:
  ```csharp
  private UIHub Hub => field ??= (UIHub)CircuitHub;
  private IStringLocalizer L => Hub.StringLocalizer;
  ```
  (`ReconnectBanner` on Fusion's `StatefulComponentBase<TState>` is the only case.)
- Only if the base has no hub at all — a plain Blazor input base — fall back to
  `[Inject] private IStringLocalizer L { get; init; } = null!;`. Today that is
  `TextBox : InputText` and nothing else. Add a one-line comment saying why the
  base is forced.

### Services

Derive from `UIServiceBase<THub>`, which exposes `L` the same way. Only a service
with no `UIServiceBase` base should lazy-resolve:

```csharp
private IStringLocalizer L => field ??= Services.GetRequiredService<IStringLocalizer>();
```

A `static` helper taking a hub reads it off the hub: `var l = hub.StringLocalizer;`

A plain class constructed by a factory delegate takes it as a constructor
parameter, and the registration resolves it — `WindowsAppSettings` is the worked
example:

```csharp
services.AddTransient<INativeAppSettings>(
    c => new WindowsAppSettings(c.GetRequiredService<IStringLocalizer>()));
```

`IStringLocalizer` is **scoped**, so this only works where the resolving provider
is the Blazor circuit's scope.

## Patterns that need care

### Counted text — one key, forms separated by `|`

`{0} member` / `Delete message?` is a single key whose value lists that
language's plural forms separated by `|`, in the order `PluralRules` indexes
them — one, few, many:

```json
"en": "{0} member|{0} members",
"ru": "{0} участник|{0} участника|{0} участников",
"ja": "メンバー {0} 人"
```

A language lists only as many forms as it needs; the index is clamped to the
last one, which is also where the English fallback lands. Listing *more* forms
than the language has leaves one unreachable — `EveryPluralKeyHasFormsForItsLanguage`
catches that.

The typed member takes the count **first** — `L.Chat_Members(count, count)` —
because the value formatted in is not always the count itself (`ChatMemberCounter`
passes `"1.2K"`).

**Do not** go back to `_One`/`_Other` key pairs picked by a `count == 1 ?` at the
call site: that renders Russian and Ukrainian as "2 участников".

**A new language needs its own rule, and the families are not interchangeable.**
`PluralRules` has three branches, and `PluralLocalizerExtTest` fails until a newly
shipped language adds counted cases to its table:

- **East Slavic and BCMS** (ru, uk, sr, hr, bs, cnr) — 21 is *one*: "21 участник".
- **Polish** — only a bare 1 is *one*, so 21 is *many*: "21 plików", never
  "21 plik". Reusing the Slavic branch mis-inflects every count ending in 1
  above 20.
- **Czech** — *few* is a plain 2-4 with no mod-100 exception.
- Everything else takes the two-form default; fr, hi and pt count zero as
  singular. Languages that don't inflect for number (id, ja, ko, zh, vi, tr)
  ship a single form.

### Sentence fragments — `_Prefix` / `Target` / `_Suffix`

When a sentence wraps a child component or an emphasized span, split it into
three keys rather than concatenating at the call site:

```razor
@L.Banner_LockScreenCalls_Prefix(CoreConstants.AppName)<strong
    >@L.Banner_LockScreenCallsTarget</strong>@L.Banner_LockScreenCalls_Suffix
```

Rules for the trio:

- The names are `X_Prefix`, `XTarget` (no underscore), `X_Suffix`.
  `EverySentenceFragmentPairHasContent` derives the suffix key from the prefix key
  by name, so **the `_Prefix`/`_Suffix` spelling is load-bearing** — a `_Format`
  suffix would break the pairing even when the value carries a `{0}`.
- Any `{0}` argument lives on the **`_Prefix`** member. The target and suffix
  members take no arguments, so a `{0}` there would render literally.
- **Either side may be empty**, and often must be: word order differs, so
  Japanese puts the whole sentence in the prefix and the verb in the suffix while
  English leaves the suffix `""`. Only both sides being empty is an error.
- The `<strong\n    >` split-tag is deliberate — it keeps the whitespace out of
  the emphasized span without introducing a text node.

### Enums are never rendered raw

`@Scope.ToString()` in markup ships an English enum name in every language. Map
the enum through a switch to catalog keys instead:

```csharp
private string GetScopeTitle(SearchScope scope)
    => scope switch {
        SearchScope.People => L.Search_TypePeople,
        SearchScope.Groups => L.Search_TypeGroups,
        ...
    };
```

The same applies to a `static` helper returning display text — make it an
instance method so it can reach `L`.

### Strings hiding inside C# expressions

An attribute/text-node scan will not find text living in a ternary, a `??`
fallback, or a local declared in an `@{ }` block. Those are still user-visible
and still need a key. The plan doc carries a
[scanner for exactly this case](./plans/localization-remaining.md).

## Writing English that can be translated

**Agreement is the translator's problem, and English hides it.**

- A key whose value is a bare adjective or participle can only be shared where
  the noun it agrees with is the same. `Chat_Public` and `Place_Public` are
  separate keys because *чат* is masculine and *место* neuter, and Italian needs
  *pubblica* for one and *pubblico* for the other. **Changing the noun a bare
  adjective agrees with means revisiting that adjective's key** in every
  gendered language.
- Text about a person must not assume their gender — "Прочитано", not "Прочитал".
- A name spliced into a sentence has to land where no inflection is required. In
  Russian and Ukrainian that means **after a colon**, not after a preposition that
  would demand a case. `Unavailable_NotFound_Format` is `"Not found: {0}"` for
  exactly this reason.
- Watch the preposition a noun governs. Russian «в Место» but «на Площадку»;
  swapping the term means rewriting every string that puts a preposition in front
  of it, not just the term itself.

## What is deliberately NOT localized

This list is exhaustive on purpose — anything not on it should have a key. The
decision rule that routes a string to this list or to a key lives in
[CODING_STYLE.md → "When a string is localization's business"](CODING_STYLE.md#when-a-string-is-localizations-business);
keep the two in sync when either changes.

**Strings no user reads** are out of scope entirely and need no justification:
log messages, CSS classes, element ids, JS interop method names, Kvas keys, state
categories, HTTP headers, test data. The entries below are the ones a user *does*
see and that stay English anyway.

**Diagnostics panels.** The bodies of `VideoDiagnosticsModal.razor` and
`AudioDiagnosticsModal.razor` (~165 technical labels: `Coded`, `cap binding`,
`Union display slots`, layer caps, verdicts) stay hardcoded English. *A
diagnostics readout is like a log line* — it is read against source, docs and
support threads that are all in English, so translating it breaks that
correspondence and makes a bug report harder to act on, not easier. The same
reasoning covers `LogView`'s log output.

The boundary is the modal: the **entry points** into diagnostics *are* localized,
because they are ordinary UI chrome — the
`DevTools_Enable{Video,Audio}Diagnostics` toggles, the `Diagnostics_Video` menu
item, the `Diagnostics_Audio` tooltip. Stop there.

**Error messages raised as exceptions** — see [Errors and server messages](#errors-and-server-messages)
below. They keep their English literal at the throw site *by design*.

**Brand and product names**: `GIF`, `Google Play`, `App Store`, `Microsoft Store`,
`KLIPY`, `Sentry`, `Firebase Analytics`, `Live Activities`.

**Asset identifiers in `alt` attributes**: `Web/Chrome/01`, `Tutorial slide #1` —
these name a screenshot, they are not prose.

**Magic literals the user must type back.** `DeleteAccountModal` asks the user to
type `DELETE`; the literal is compared against input, so it must stay English in
every language.

**Developer surfaces**: test pages (`*TestPage.razor`, `Pages/Test/`, `Testing/`),
admin-only pages and menus (`AdminCopyChatToPlacePage`, `AccountStatusMenu`),
`CaptchaView`'s fake-reCAPTCHA branch, mockup text behind `EnableIncompleteUI`
(`PlaceInfo`'s follower block), and the `/test/discover` Discover prototype.

**Commented-out markup.** Three `ChatPropertiesMenu` entries sit inside a
`@* … *@` block; a scanner that doesn't strip razor comments will keep reporting
them. They get keys if and when the code is uncommented, not before.

**`Date_*Pattern` values** — `HH:mm`, `d MMMM yyyy` and friends are
`DateTimeFormatInfo` format specifiers. They are *translated* in the sense that
each locale picks its own order and separators, but they must stay in Latin
letters: `HH` is a format token, not the letter H.

**Developer invariants thrown from markup**: `"<Tab> component must be nested into
<TabPanel>"` and friends. Not catalog material.

**Landing pages and legal docs** (`Pages/Landing/`, including the privacy, terms
and cookie documents). These sit before sign-in, the marketing half needs
per-language routes before translation pays off, and the legal half is a
liability decision. See the plan doc §5.

## Errors and server messages

**Anything raised as an exception and surfaced through `UICommander.ShowError`
must keep its English literal at the throw site.**
`LocalizingUIActionFailureTracker` localizes it at render time via
`LocalizationUI.Get`, which matches against the **English** `MessageIndex`.
Calling `L` at the throw site produces a pre-translated message that misses the
index, gets queued for an AI translation of already-translated text — a wasted
call, and unreviewed wording replacing the catalog's.

To make such a message translatable:

1. Add the English text as an `Error_*` key in `Messages.<lang>.json`.
2. Put the literal in a `StandardError` helper —
   `StandardError.Upload.FileTooBig(maxSizeMb)` is the worked example.

**Never write the literal inline in a `.razor` file.**
`ServerErrorLocalizationTest` anchors every `Error_*` key to a literal in `*.cs`
only, so a message thrown from markup cannot be catalogued at all. The scan is
narrow on purpose: an inline message gets copied to the next call site rather
than shared, which is how the file-size error acquired four different spellings.

Dynamic text composed on the server that crosses RPC is likewise **not** catalog
material — it is localized at runtime via `LocalizationUI.Get` (AI translation).
See `LocalizingUIActionFailureTracker` for the pattern.

## Terminology

Product terms must be translated consistently across all 1252 keys, and in
languages that have case, marked as terms by **capitalizing them mid-sentence**
so they don't read as a generic noun.

### Place

A container of chats plus a shared community. Translated as *place in the
location sense*, never as "space":

| | Place | | | Place | | | Place |
|---|---|---|---|---|---|---|---|
| en | Place | | pt | Lugar | | bs | Mjesto |
| ru | Место | | tr | Mekân | | hr | Mjesto |
| uk | Місце | | vi | Địa điểm | | cnr | Mjesto |
| es | Lugar | | ja | プレイス | | sr | Место |
| fr | Lieu | | ko | 플레이스 | | pl | Miejsce |
| it | Luogo | | hi | प्लेस | | cs | Místo |
| de | Place | | zh | 地点 | | bg | Място |
| | | | | | | id | Tempat |

German keeps the English loanword: German capitalizes every noun, so a native
word would not signal "product term". Japanese, Korean and Hindi transliterate,
which is how those languages mark a product name when capitalization isn't
available. Turkish uses *Mekân* rather than *Yer* because `yer` + dative
possessive gives `yerine`, which also means "instead of".

Watch the **preposition** a noun governs when picking a term: Russian «в Место»
but «на Площадку». Swapping the term means rewriting every string that puts a
preposition in front of it, not just the term itself.

`LocationMessage_Place` is **not** this term — it labels a pin dropped on a map,
and takes each language's plain geographic word (de `Ort`, ja 場所, ko 장소,
hi स्थान, ru `Место` lowercase-sense).

### Public / Private

An *access mode*, so a language with a native open/closed antonym pair uses it
rather than calquing the English:

| | Public / Private | | | Public / Private |
|---|---|---|---|---|
| ru | Открытый / Закрытый | | cs | Otevřený / Uzavřený |
| uk | Відкритий / Закритий | | bg | Отворен / Затворен |
| pl | Otwarty / Zamknięty | | bs, hr, cnr | Otvoren / Zatvoren |
| id | Terbuka / Tertutup | | sr | Отворен / Затворен |

The pair is symmetric and native, it matches what `Place_PublicHint` and
`Place_PrivateHint` actually describe (a link anyone can open vs.
invitation-only), and «публичный» / «приватный» read as tech-translation. This
covers `{Chat,Place}_{Public,Private}`, `{Chat,Place}_{Public,Private}{Chat,Place}`,
`Chat_*ChatThread` and `LeftPanel_PublicChatsAndPlaces`.

The **link** keys are a different sense and keep the borrowed pair —
`ChatWelcome_PublicLink`, `ChatWelcome_PrivateJoinLink`, `Invite_NewPrivateLink`.
A URL isn't "open" or "closed"; the adjective describes who may use it.

### Cookies

**An HTTP cookie is a technical term, and must not be rendered as the food.**
«Печеньки», "kolačići", "biscotti" and friends are calques of the *snack*; a
reader looking for a cookie policy does not recognise them. Use whichever of
these the locale actually uses for the web technology:

- **The bare English term** where that is the norm: en, de, es, fr, pt, it, zh,
  ja, vi, id.
- **Native word for "files" + the Latin token `cookie`**, which is the house
  style across the Slavic catalogs: ru `Файлы cookie`, uk `Файли cookie`,
  pl `Pliki cookie`, cs `Soubory cookie`, bg `Файлове cookie`,
  bs/cnr `Cookie fajlovi`, hr `Cookie datoteke`, sr `Cookie фајлови`.
- **A transliteration** where the locale genuinely transliterates: ko `쿠키`,
  hi `कुकीज़`.

The test is "is this what people in that market actually call the web
technology", not "is there a native word for the biscuit". Turkish `Çerezler` is
literally "snacks" but *is* the established Turkish term for HTTP cookies —
that's the one case where the food word is correct, and it stays.

### Other shared terms

- **Member** — the person, not the abstract "membership": pl `uczestnik`,
  cs `člen`, bg `участник`, BCMS `član`, id `anggota`.
- **Push-to-talk** — translated, not left in English: pl `Naciśnij i mów`,
  cs `Stiskni a mluv`, bg `Натисни и говори`, BCMS `Pritisni i govori`,
  id `Tekan untuk bicara`.
- **Chat** — kept as `chat` where the locale borrows it (pl `czat`, BCMS Latin
  `chat`), but Serbian Cyrillic uses `чет` rather than leaving Latin text inside
  a Cyrillic sentence.
- **Register** — informal second person, matching the English voice: pl `Ty`,
  ru/uk polite-informal «вы», BCMS `vi`.

## Derived catalogs (BCMS)

Bosnian, Croatian, Montenegrin and Serbian are four standards of one language.
Translating them independently would produce four near-copies that drift apart
wherever a translator happened to word something differently — hiding the places
they genuinely differ. So **`bs` is the hand-written base** (ijekavian, Latin) and
`cnr`, `hr` and `sr` are generated from it by
[`scripts/derive-bcms.cmd`](../scripts/derive-bcms.cmd):

- `cnr` — Bosnian with Serbian-style month names and `-šć-` for `-št-`.
- `hr` — same ijekavian reflexes, different lexicon (`datoteka` not `fajl`,
  `sučelje` not `interfejs`) and wholly different month names (`siječanj`).
- `sr` — ijekavian → ekavian (`mjesto` → `mesto`), then Latin → Cyrillic.

**Edit `Strings.bs.json` / `Messages.bs.json` and re-run the script; never
hand-edit the derived files.** `scripts/derive-bcms.cmd --check` regenerates into
memory and fails if the files on disk disagree, which is what keeps that rule
enforceable.

Two traps the script encodes, worth knowing if you touch it:

- **`Date_*Pattern` values are format specifiers, not prose.** Transliterating
  `HH:mm` to `ХХ:мм` makes every timestamp unparseable, so those keys are copied
  through verbatim.
- **Brands and protocol words must survive transliteration** — `Windows`,
  `macOS`, `reCAPTCHA`, `API`, `cookie` and friends stay Latin, together with any
  case suffix glued to them (`Windowsu`, not `Wиндоwсу`).

## How it's enforced

| Test | What it guards |
|---|---|
| `AppLocalizationTest` | Every catalog defines exactly the English key set; every key is translated in every language; placeholders survive translation; members and keys correspond 1:1; every member reads the key it's named after and resolves non-empty in all 14 languages; plural form counts; `_Prefix`/`_Suffix` pairs; the two catalogs share no keys |
| `ServerErrorLocalizationTest` | Every `Error_*` key byte-matches a literal the code still throws, scanning `*.cs` only |
| `ValidationMessageLocalizationTest` | Both validation routes — BCL attributes reverse-matched through `MessageIndex`, and our own attributes reporting a key directly |
| `SystemEntryLocalizationTest` | Every `[Union]` system-entry kind is covered, so a new kind can't ship unlocalized |
| `FormSectionLocalizationTest` | A validation message renders with the section's `Label`, not the member name |
| `PluralLocalizerExtTest`, `DateFormatsLocalizerExtTest` | Form selection and the ICU-free `DateTimeFormatInfo` |
| `tests/ts/e2e/ui-localization-smoke.test.ts` | End-to-end: with each language selected, no visible text equals an English catalog value whose translation differs — and each screen shows *some* translated text, so a language that failed to apply can't pass vacuously |

`Validation_*` keys are excluded from the member-correspondence check: they are
resolved by key from `ActualChat.Core`, which can't reference `LocalizerExt`.

## Where the UI language comes from

**The account owns it.** `UserLanguageSettings.UILanguage` is a nullable
`Language` synced through `LanguageUI.Settings`, so changing it in one app
changes it in every app signed into the same account. `null` is not "unset" — it
is the **auto** selection, meaning "follow the device".

The device still decides the first frame, because the app has to render before it
can reach the server:

| Value | Where | What it is |
|---|---|---|
| `Settings.Value.UILanguage` | server, per user | the selection; `null` = auto |
| `BrowserInfo.StoredUILanguage` | `localStorage['ui.language']` | the cached selection read at startup |
| `BrowserInfo.UILanguage` | — | the cached selection, or the detected device language for auto |
| `LocalizationUI.Language` | — | `BrowserInfo.UILanguage`, fixed for this app instance |

`LocalizationUI.Language` is what `AppStringLocalizer` reads, and it is a plain
property rather than a state: the localizer is read synchronously from ~1200 call
sites, so it is pulled once — in `AppScopedServiceStarter.PrepareFirstRender`,
right after `BrowserInfo.WhenReady` and before anything of the app renders — and
never changes afterwards. A component that rendered before it landed would stay
English, which is why the pull happens there and not later.

`localization-ui.ts` mirrors `theme.ts`: `localStorage` rather than `LocalSettings`,
so it is readable at bundle load (before Blazor exists) and survives a session
change, and it rides to .NET on `BrowserInfo.InitResult` at no extra round trip.
The catalog list stays in C# — JS reports `navigator.languages` verbatim and
`Languages.DetectUILanguage` does the matching, by `IsoCode`, so `en-GB` and a bare `en`
both land on the one `en` catalog.

**Changing it does not reload the app.** `LanguageUI`'s `SyncUILanguage` chain
watches `Settings` and mirrors the account value into the device cache. The
running app keeps the `LocalizationUI.Language` selected at startup; the cached
choice takes effect when the user manually reloads or next starts the app. The
same path handles local and remote account changes because `Settings` is a
`MutableState`, so its `Changes` fires locally too.

Do not confuse any of this with the *spoken*/transcription languages —
`Primary`/`Secondary`/`Tertiary` on the same record, and `GetChatLanguage` for
the per-chat override. Same service, two unrelated concepts.

**What is still English regardless:** push notification text composed on the
server, the iOS share extension, Android permission dialogs and every OS prompt.
See §3 and §4 of [what's left](plans/localization-remaining.md).

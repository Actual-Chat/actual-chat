# Localization (i18n)

Voxt ships its UI in **22 real languages**, plus the hidden `Max` pseudo-locale
for layout testing. This document is the complete set of rules for adding,
translating and consuming user-visible text.

> The one rule: **never hardcode user-visible English text in UI code.**
> Everything else here is either a mechanism that supports that rule or a
> deliberate, enumerated exception to it.

The supported languages are declared in one place — `Languages.AllUI`
(`src/dotnet/Api/Identifiers/Languages.cs`):

| | | | |
|---|---|---|---|
| English (default) | Español | Français | Italiano |
| Русский | Deutsch | 中文 | हिन्दी |
| 日本語 | 한국어 | Português | Türkçe |
| Українська | Tiếng Việt | Polski | Bahasa Indonesia |
| Čeština | Български | Bosanski | Hrvatski |
| Crnogorski | Српски | | |

A language can be usable for the UI, for transcription, or both — `Language.Support`
carries a `LanguageSupport` flag, and `Languages` exposes the two sets separately:

- **`Languages.AllUI`** — ships a catalog, so the app can render in it. Declared as an
  ordered array because that order is what the App-language picker shows;
  `LanguageSupportTest` keeps it in agreement with the flag.
- **`Languages.AllUIAndTestOnly`** — `AllUI` plus URL-only pseudo-locales whose catalogs
  the runtime must load. It currently adds only `Languages.Max`; never use this set
  for a picker or an account setting.
- **`Languages.AllTranscription`** — offered as a spoken language and accepted by a
  transcriber. Derived from the flag.
- **`Languages.All`** — the union, and what `Language.Parse` resolves against.

The two sets are not the same. Montenegrin ships a UI catalog but no transcriber knows
its `cnr` code, so it is `LanguageSupport.UI` only and never reaches the spoken-language
picker. Most declared languages are the other way round: transcription-only.

Only the **canonical variant** of an `IsoCode` carries `LanguageSupport.UI` — `en-GB`,
`en-IN`, `zh-TW`, `fr-CA`, `pt-BR` and the Spanish variants all resolve to a catalog
their base language already owns.

For what is still *unlocalized* and in what order it will be picked up, see
[the localization plan](./plans/localization-remaining.md). That doc tracks
remaining work; this one carries the rules.

## How the catalog works

Two embedded JSON catalogs per language live in
`src/dotnet/Localization/Resources/`:

- **`Strings.<iso>.json`** — ordinary UI text, addressed by key. 1315 keys.
- **`Messages.<iso>.json`** — server errors and validation messages, reverse-indexed
  by `MessageIndex` so an English message produced at runtime can be matched back
  to its key. 103 keys.

A key belongs to **exactly one** catalog: `StringCatalog` merges both into a
single forward lookup, so a shared key would make one silently shadow the other.
`AppLocalizationTest.CatalogsShouldNotShareKeys` enforces this.

The project is `ActualChat.Localization`, and it is deliberately
dependency-free — `ActualChat.Api` plus `Microsoft.Extensions.Localization`,
nothing from the UI — so backend services and, in time, the native extensions can
reference it without dragging in the Blazor UI assembly and its 2.2 MB of
embedded catalogs. The namespace matches the assembly; it was
`ActualChat.UI.Blazor.Resources` until the rename, which was worth doing once the
non-UI consumers (`NotificationsBackend`, `UserLocalizers`, `WindowsAppSettings`)
made a Blazor-shaped namespace read as a dependency they do not have. The code
files sit in `Resources/` beside the JSON, and that folder deliberately
contributes no namespace segment — `Localization.csproj.DotSettings` tells
ReSharper to skip it.

Both files are **JSONC** — `//` comments and trailing commas are allowed, and the
catalogs use blank lines and comments to group related keys. Keep a new key next
to its group rather than appending it at the end.

**Only the English catalogs carry those comments, and they are written for a
translator.** Each group in `Strings.en.json` opens with a comment saying where it
appears on screen and what it is really about, because that is exactly what a value
like `"Show details"` cannot convey — the key it replaced said `Items`, and half the
catalogs duly translated it as *messages*. The file's own header explains the
placeholder, plural and `_Prefix`/`_Suffix` notation. The Max generator copies these
comments into `Strings.max.json`; the BCMS one derives from `Strings.bs.json`, which
has none, so the derived language catalogs stay comment-free.

Lookup is `StringCatalog`, resolved against a language by one of two
`IStringLocalizer`s. The standard `.resx` / `CultureInfo` machinery does **not**
work here: the app runs under `InvariantGlobalization`, which is also why month
and day names come from `Date_*` catalog keys via `DateFormatsLocalizerExt`
rather than from ICU.

| Localizer | Where | Language from |
|---|---|---|
| `AppStringLocalizer` (`src/dotnet/UI.Blazor.App/Services/`) | the app, scoped to the Blazor circuit | `LocalizationUI.Language`, read per lookup |
| `LanguageStringLocalizer` (`src/dotnet/Localization/Resources/`) | server-side code composing text *for* a user, and the iOS share extension | an explicit `Language`, passed in; cached per language |

**Server code composing text for a user must resolve
`UILanguage ?? DetectedUILanguage ?? Languages.Main`** — the account's explicit
selection, else what "follow the device" resolved to on that user's device, else
English. It must **not** use `Primary`: that is a *spoken* language and says
nothing about what the app renders in. `UserLocalizers` (`Users.Contracts`) is
that resolution as an injectable service — use it rather than re-deriving the
chain; `NotificationsBackend` is the worked caller.

**Missing keys never throw.** `GetString` falls back to English, and then to the
key name itself with `resourceNotFound: true`. A key rendered as
`Settings_Something` on screen means the key is absent from every catalog.

## Adding a key

Three edits, all enforced by `AppLocalizationTest`:

1. Add it to `Strings.en.json` **and every hand-written real-language
   `Strings.*.json`**. All 22 real languages must define exactly the English key
   set — no more, no less. Then regenerate the BCMS and Max catalogs; see
   [Derived catalogs](#derived-catalogs-bcms) and [the Max catalog](#derived-max-catalog).
   If the key opens a new group, give the group a context comment in
   `Strings.en.json` in the style of the ones already there.
2. Add the matching typed member to
   `src/dotnet/Localization/Resources/LocalizedStringsLocalizerExt.cs`. One member
   per key, names matching exactly.
3. Use it from code (see [Consuming strings](#consuming-strings)).

### Key naming

`Group_Name` in PascalCase, where the group mirrors the component, page or
feature: `ChatMenu_Pin`, `Settings_Title`, `ErrorToast_ActionFailed`. A one-off
group for a single component is fine and common (`Reconnect_`, `Redirect_`,
`ServerInstance_`).

Format strings get a **`_Format` suffix** and `{0}`-style placeholders. Every
translation must keep every placeholder the English value has —
`EveryShippedTranslationShouldMatchEnglishKeys` checks this per key, and
`EveryLocalizerExtMemberResolvesInEveryLanguage` additionally invokes each member
and fails if the resolved value drops an argument.

## Consuming strings

Always go through the typed members in `LocalizedStringsLocalizerExt`
(`@L.ChatMenu_Pin`, `L.Settings_Quit_Format(appName)`), **never** the raw
`L["..."]` indexer — the typed members make a typo a compile error, and
`LocalizerExtMembersMatchEnglishKeysExactly` keeps members and keys in
one-to-one correspondence.

### Components

Use the `L` property that the `UIHub` base classes already expose. **If a
component has no such base, give it one — do NOT add `[Inject] private
IStringLocalizer L`.** Every base in `src/dotnet/UI.Blazor/BaseTypes/` exposes `L`
(plus `Hub` and the usual service shortcuts), so pick the one matching what the
component already does:

| Component currently | Change `@inherits` to |
|---|---|
| plain `ComponentBase` / no `@inherits` | `ComponentBase<UIHub>` |
| `FusionComponentBase` | `FusionComponentBase<UIHub>` |
| `ComputedStateComponent<TState>` | `ComputedStateComponent<UIHub, TState>` |
| `ComputedRenderStateComponent<TState>` | `ComputedRenderStateComponent<UIHub, TState>` |

In `UI.Blazor.App` use `AppUIHub` instead of `UIHub`. Swapping the base is a
one-line change and costs nothing at runtime — `L` is just `Hub.StringLocalizer`.

**When no wrapper fits** (the component is stuck on a framework or Fusion base),
do *not* write a new `<THub, …>` wrapper for a single consumer — each wrapper
re-declares ~20 shortcut properties, so one is only worth it once several
components share the base. Instead:

- If the base derives from `CircuitHubComponentBase`, the hub is **already
  injected** — just type it, the same way `ComputedStateComponent<THub, TState>`
  does internally. Two lines, no new type:
  ```csharp
  private UIHub Hub => field ??= (UIHub)CircuitHub;
  private IStringLocalizer L => Hub.StringLocalizer;
  ```
  (`ReconnectBanner` on Fusion's `StatefulComponentBase<TState>` is the only case.)
- Only if the base has no hub at all — a plain Blazor input base — fall back to
  `[Inject] private IStringLocalizer L { get; init; } = null!;`. Today that is
  `TextBox : InputText` and nothing else. Add a one-line comment saying why the
  base is forced.

### Services

Derive from `UIServiceBase<THub>`, which exposes `L` the same way. Only a service
with no `UIServiceBase` base should lazy-resolve:

```csharp
private IStringLocalizer L => field ??= Services.GetRequiredService<IStringLocalizer>();
```

A `static` helper taking a hub reads it off the hub: `var l = hub.StringLocalizer;`

A plain class constructed by a factory delegate takes it as a constructor
parameter, and the registration resolves it — `WindowsAppSettings` is the worked
example:

```csharp
services.AddTransient<INativeAppSettings>(
    c => new WindowsAppSettings(c.GetRequiredService<IStringLocalizer>()));
```

`IStringLocalizer` is **scoped**, so this only works where the resolving provider
is the Blazor circuit's scope.

## Patterns that need care

### Counted text — one key, forms separated by `|`

`{0} member` / `Delete message?` is a single key whose value lists that
language's plural forms separated by `|`, in the order `PluralRules` indexes
them — one, few, many:

```json
"en": "{0} member|{0} members",
"ru": "{0} участник|{0} участника|{0} участников",
"ja": "メンバー {0} 人"
```

A language lists only as many forms as it needs; the index is clamped to the
last one, which is also where the English fallback lands. Listing *more* forms
than the language has leaves one unreachable — `EveryPluralKeyHasFormsForItsLanguage`
catches that.

The typed member takes the count **first** — `L.Chat_Members(count, count)` —
because the value formatted in is not always the count itself (`ChatMemberCounter`
passes `"1.2K"`).

**Do not** go back to `_One`/`_Other` key pairs picked by a `count == 1 ?` at the
call site: that renders Russian and Ukrainian as "2 участников".

**A new language needs its own rule, and the families are not interchangeable.**
`PluralRules` has three branches, and `PluralLocalizerExtTest` fails until a newly
shipped language adds counted cases to its table:

- **East Slavic and BCMS** (ru, uk, sr, hr, bs, cnr) — 21 is *one*: "21 участник".
- **Polish** — only a bare 1 is *one*, so 21 is *many*: "21 plików", never
  "21 plik". Reusing the Slavic branch mis-inflects every count ending in 1
  above 20.
- **Czech** — *few* is a plain 2-4 with no mod-100 exception.
- Everything else takes the two-form default; fr, hi and pt count zero as
  singular. Languages that don't inflect for number (id, ja, ko, zh, vi, tr)
  ship a single form.

### Sentence fragments — `_Prefix` / `Target` / `_Suffix`

When a sentence wraps a child component or an emphasized span, split it into
three keys rather than concatenating at the call site:

```razor
@L.Banner_LockScreenCalls_Prefix(CoreConstants.AppName)<strong
    >@L.Banner_LockScreenCallsTarget</strong>@L.Banner_LockScreenCalls_Suffix
```

Rules for the trio:

- The names are `X_Prefix`, `XTarget` (no underscore), `X_Suffix`.
  `EverySentenceFragmentPairHasContent` derives the suffix key from the prefix key
  by name, so **the `_Prefix`/`_Suffix` spelling is load-bearing** — a `_Format`
  suffix would break the pairing even when the value carries a `{0}`.
- Any `{0}` argument lives on the **`_Prefix`** member. The target and suffix
  members take no arguments, so a `{0}` there would render literally.
- **Either side may be empty**, and often must be: word order differs, so
  Japanese puts the whole sentence in the prefix and the verb in the suffix while
  English leaves the suffix `""`. Only both sides being empty is an error.
- The `<strong\n    >` split-tag is deliberate — it keeps the whitespace out of
  the emphasized span without introducing a text node.

### Text a data type stands in for itself

Two kinds of chat entry carry no text of their own: a **system entry** ("X has
joined the chat.") and an **empty entry** - a shared location, or a message that
is only attachments. Both are worded in C#, and both are read by three consumers
that need three different languages, so both are a `virtual` builder carried on
`IChatMarkupHub` rather than an `IStringLocalizer` parameter:

| | English base (`ActualChat.Api`) | Localized override |
|---|---|---|
| System entries | `SystemEntryMarkupBuilder.Default` | `LocalizedSystemEntryMarkupBuilder` (UI.Blazor.App) |
| Locations, attachment-only | `EmptyEntryMarkupBuilder.Default` | `LocalizedEmptyEntryMarkupBuilder` (`ActualChat.Localization`) |

`ChatMarkupHub` resolves the localized one from the circuit; `BackendChatMarkupHub`
returns `Default`. That default is not an oversight - a **link preview is cached
per content id** and an **LLM prompt** has no reader at all, so English is the only
answer either can have. Where there *is* a reader, the reader's language wins:
`EmptyEntryNotificationContent.Render` gets a `LocalizedEmptyEntryMarkupBuilder` for
the reader's language inside the notification fan-out, which is why that class takes
an `IStringLocalizer` directly rather than a service provider.

The fan-out renders a `NotificationContent` **once per language, not once per
recipient** - `EnqueueMessageRelatedNotifications` memoizes by
`IHasUILanguage.UILanguage`, so a chat with hundreds of subscribers composes as many
strings as it has languages among them. Every content kind gets this, not just the
empty-entry one. It works because the text is a function of the language alone: a
content that varied by *reader* - their name, their unread count - would be silently
wrong here.

A push is worded once per language but the entry is classified once per *entry*:
`NotificationTextComposer.Compose` decides from the entry alone whether it has text
of its own - a location, or empty content - and returns either the author's words
as a `SharedNotificationContent` or an `EmptyEntryNotificationContent` that words
itself per reader. That is the one place the notification layer looks at the entry
kind; call sites take the content and never re-derive the split.

**Add a case to the builder, never to the call site.** A consumer that special-cases
an entry kind before asking the markup layer restates the rule and drifts. The
chat list used to word a location through its own `ChatList_SentLocation` pair; those
keys are gone, and `ChatUI` calls `Build` with `MarkupConsumer.ChatListItemText` like
every other reader. The one distinction the chat list draws - a live share against a
one-shot pin - is `Build`'s `isLiveLocation` parameter. That fact isn't on the entry:
it's `SharedLocation.Duration`, which only a caller that resolved one can read, so the
call site supplies the *fact* and the builder still owns the *words*. The push resolves
it too; quotes and the pinned bar are synchronous and always read as a pin. The flag
means "was shared live", not "is still live" - `Duration` is immutable, so the push
doesn't re-word itself when the share expires.

The 📍 is not in the catalog. `EmptyEntryMarkupBuilder.LocationPin` is prepended in
code for every consumer except the chat list, whose row draws a map-point icon of its
own. An emoji has nothing to translate, and keeping it out of the values is what let
the chat list and the push share one key.

The English base is not a leftover to refactor away (#4339). `ActualChat.Api` is
published to nuget.org on every push to `dev`, and a package consumer has neither
`IChatMarkupHub` nor the catalog - `Default` is the only implementation they get. The
catalog can't be the single source because `Api` sits below `Localization`, and the
catalog can't drop the keys because every other language falls back to `en`. So the
English exists twice on purpose, and `EmptyEntryLocalizationTest` and
`SystemEntryLocalizationTest` pin the English catalog to each `Default`, so the two
renderings can't word the same event differently.

### Enums are never rendered raw

`@Scope.ToString()` in markup ships an English enum name in every language. Map
the enum through a switch to catalog keys instead:

```csharp
private string GetScopeTitle(SearchScope scope)
    => scope switch {
        SearchScope.People => L.Search_TypePeople,
        SearchScope.Groups => L.Search_TypeGroups,
        ...
    };
```

The same applies to a `static` helper returning display text — make it an
instance method so it can reach `L`.

### Strings hiding inside C# expressions

An attribute/text-node scan will not find text living in a ternary, a `??`
fallback, a local declared in an `@{ }` block, a `switch` arm, or a `[Parameter]`
default. Those are still user-visible and still need a key — #4233 found ~60 of
them, and the two shapes that hid the most were a `static` helper mapping a value
to display text and a `[Parameter]` whose initializer *was* the English.

`ui-localization-smoke.test.ts` is the check, and it has a blind spot worth
knowing: it compares rendered text against the English catalog, so a string that
is hardcoded **and** absent from the catalog has nothing to match against. About
half of #4233's findings were invisible to it for exactly that reason. Reading
the source is still the only way to find those.

## Writing English that can be translated

**Agreement is the translator's problem, and English hides it.**

- A key whose value is a bare adjective or participle can only be shared where
  the noun it agrees with is the same. `Chat_Public` and `Place_Public` are
  separate keys because *чат* is masculine and *место* neuter, and Italian needs
  *pubblica* for one and *pubblico* for the other. **Changing the noun a bare
  adjective agrees with means revisiting that adjective's key** in every
  gendered language.
- Text about a person must not assume their gender — "Прочитано", not "Прочитал".
- A name spliced into a sentence has to land where no inflection is required. In
  Russian and Ukrainian that means **after a colon**, not after a preposition that
  would demand a case. `Unavailable_NotFound_Format` is `"Not found: {0}"` for
  exactly this reason.
- Watch the preposition a noun governs. Russian «в Место» but «на Площадку»;
  swapping the term means rewriting every string that puts a preposition in front
  of it, not just the term itself.

## What is deliberately NOT localized

This list is exhaustive on purpose — anything not on it should have a key. The
decision rule that routes a string to this list or to a key lives in
[CODING_STYLE.md → "When a string is localization's business"](CODING_STYLE.md#when-a-string-is-localizations-business);
keep the two in sync when either changes.

**Strings no user reads** are out of scope entirely and need no justification:
log messages, CSS classes, element ids, JS interop method names, Kvas keys, state
categories, HTTP headers, test data. The entries below are the ones a user *does*
see and that stay English anyway.

**Diagnostics panels.** The bodies of `VideoDiagnosticsModal.razor` and
`AudioDiagnosticsModal.razor` (~165 technical labels: `Coded`, `cap binding`,
`Union display slots`, layer caps, verdicts) stay hardcoded English. *A
diagnostics readout is like a log line* — it is read against source, docs and
support threads that are all in English, so translating it breaks that
correspondence and makes a bug report harder to act on, not easier. The same
reasoning covers `LogView`'s log output.

The boundary is the modal: the **entry points** into diagnostics *are* localized,
because they are ordinary UI chrome — the
`DevTools_Enable{Video,Audio}Diagnostics` toggles, the `Diagnostics_Video` menu
item, the `Diagnostics_Audio` tooltip. Stop there.

**Error messages raised as exceptions** — see [Errors and server messages](#errors-and-server-messages)
below. They keep their English literal at the throw site *by design*.

**Brand and product names**: `GIF`, `Google Play`, `App Store`, `Microsoft Store`,
`KLIPY`, `Sentry`, `Firebase Analytics`, `Live Activities`.

**Asset identifiers in `alt` attributes**: `Web/Chrome/01`, `Tutorial slide #1` —
these name a screenshot, they are not prose.

**Magic literals the user must type back.** `DeleteAccountModal` asks the user to
type `DELETE`; the literal is compared against input, so it must stay English in
every language.

**Titles that become data.** A chat title is persisted once at creation and read
back by everyone in the chat, so it is content rather than chrome — translating it
would bake the *creator's* language into what the other participants see. This
covers the built-in `Notes` chat, a new Place's `Welcome` chat, and
`AuthorUI.StartAnonymousPeerChat`'s `Anonymous chat (<date>)`, whose date is
formatted invariantly for the same reason.

**Developer surfaces**: test pages (`*TestPage.razor`, `Pages/Test/`, `Testing/`),
admin-only pages and menus (`AdminCopyChatToPlacePage`, `AccountStatusMenu`),
`CaptchaView`'s fake-reCAPTCHA branch, mockup text behind `EnableIncompleteUI`
(`PlaceInfo`'s follower block), and the `/test/discover` Discover prototype.

**Commented-out markup.** Three `ChatPropertiesMenu` entries sit inside a
`@* … *@` block; a scanner that doesn't strip razor comments will keep reporting
them. They get keys if and when the code is uncommented, not before.

**`Date_*Pattern` values** — `HH:mm`, `d MMMM yyyy` and friends are
`DateTimeFormatInfo` format specifiers. They are *translated* in the sense that
each locale picks its own order and separators, but they must stay in Latin
letters: `HH` is a format token, not the letter H.

**Developer invariants thrown from markup**: `"<Tab> component must be nested into <TabPanel>"`
and friends. Not catalog material.

**Landing pages and legal docs** (`Pages/Landing/`, including the privacy, terms
and cookie documents). These sit before sign-in, the marketing half needs
per-language routes before translation pays off, and the legal half is a
liability decision. See the plan doc §5.

## Errors and server messages

**Anything raised as an exception and surfaced through `UICommander.ShowError`
must keep its English literal at the throw site.**
`LocalizingUIActionFailureTracker` localizes it at render time via
`LocalizationUI.Get`, which matches against the **English** `MessageIndex`.
Calling `L` at the throw site produces a pre-translated message that misses the
index, gets queued for an AI translation of already-translated text — a wasted
call, and unreviewed wording replacing the catalog's.

To make such a message translatable:

1. Add the English text as an `Error_*` key in `Messages.<lang>.json`.
2. Put the literal in a `StandardError` helper —
   `StandardError.Upload.FileTooBig(maxSizeMb)` is the worked example.

**Never write the literal inline in a `.razor` file.**
`ServerErrorLocalizationTest` anchors every `Error_*` key to a literal in `*.cs`
only, so a message thrown from markup cannot be catalogued at all. The scan is
narrow on purpose: an inline message gets copied to the next call site rather
than shared, which is how the file-size error acquired four different spellings.

Dynamic text composed on the server that crosses RPC is likewise **not** catalog
material — it is localized at runtime via `LocalizationUI.Get` (AI translation).
See `LocalizingUIActionFailureTracker` for the pattern.

## Terminology

Product terms must be translated consistently across all 1315 keys, and in
languages that have case, marked as terms by **capitalizing them mid-sentence**
so they don't read as a generic noun.

### Place

A container of chats plus a shared community. Translated as *place in the
location sense*, never as "space":

| | Place | | | Place | | | Place |
|---|---|---|---|---|---|---|---|
| en | Place | | pt | Lugar | | bs | Mjesto |
| ru | Место | | tr | Mekân | | hr | Mjesto |
| uk | Місце | | vi | Địa điểm | | cnr | Mjesto |
| es | Lugar | | ja | プレイス | | sr | Место |
| fr | Lieu | | ko | 플레이스 | | pl | Miejsce |
| it | Luogo | | hi | प्लेस | | cs | Místo |
| de | Place | | zh | 地点 | | bg | Място |
| | | | | | | id | Tempat |

German keeps the English loanword: German capitalizes every noun, so a native
word would not signal "product term". Japanese, Korean and Hindi transliterate,
which is how those languages mark a product name when capitalization isn't
available. Turkish uses *Mekân* rather than *Yer* because `yer` + dative
possessive gives `yerine`, which also means "instead of".

Watch the **preposition** a noun governs when picking a term: Russian «в Место»
but «на Площадку». Swapping the term means rewriting every string that puts a
preposition in front of it, not just the term itself.

`LocationMessage_Place` is **not** this term — it labels a pin dropped on a map,
and takes each language's plain geographic word (de `Ort`, ja 場所, ko 장소,
hi स्थान, ru `Место` lowercase-sense).

### Public / Private

An *access mode*, so a language with a native open/closed antonym pair uses it
rather than calquing the English:

| | Public / Private | | | Public / Private |
|---|---|---|---|---|
| ru | Открытый / Закрытый | | cs | Otevřený / Uzavřený |
| uk | Відкритий / Закритий | | bg | Отворен / Затворен |
| pl | Otwarty / Zamknięty | | bs, hr, cnr | Otvoren / Zatvoren |
| id | Terbuka / Tertutup | | sr | Отворен / Затворен |

The pair is symmetric and native, it matches what `Place_PublicHint` and
`Place_PrivateHint` actually describe (a link anyone can open vs.
invitation-only), and «публичный» / «приватный» read as tech-translation. This
covers `{Chat,Place}_{Public,Private}`, `{Chat,Place}_{Public,Private}{Chat,Place}`,
`Chat_*ChatThread` and `LeftPanel_PublicChatsAndPlaces`.

The **link** keys are a different sense and keep the borrowed pair —
`ChatWelcome_PublicLink`, `ChatWelcome_PrivateJoinLink`, `Invite_NewPrivateLink`.
A URL isn't "open" or "closed"; the adjective describes who may use it.

### Register

**Voxt addresses the user politely.** English has one "you" and hides the
decision; most other shipped languages make it every time they put a verb or a
pronoun on screen, and a catalog that picks differently in different places
reads as sloppy rather than friendly.

The rule: **in every language that marks a T–V distinction, use the V form** —
ru/uk «вы»/«ви», cs `vy`, bg 2nd person plural, BCMS `vi`, de `Sie`, fr `vous`,
tr `siz`, id `Anda`, hi आप, ja です/ます, ko 해요체. That covers buttons and menu
entries as much as prose: a short label is still the app talking to a person.

Two things that look like exceptions and are not:

- **A register-neutral form is fine where the language uses one for UI.** ru, uk
  and cs label buttons and menu entries with the **infinitive** — «Сохранить»,
  «Скасувати», `Uložit` — which is the native UI convention and takes no side on
  T–V. Keep it; the polite form is what those catalogs use the moment a string
  addresses the user in the second person («Выберите камеру», `Vyberte kameru`).
- **Polish stays as it is.** The Polish V form is `Pan`/`Pani` plus the third
  person, and no mainstream consumer app uses it — Polish software labels
  buttons with the 2sg imperative (`Zapisz`, `Dołącz`) and says `Ty`/`Twój` in
  prose. Converting it would read as stilted, not respectful. Same reasoning
  applies to Spanish `tú`, Italian `tu` and Chinese 你, where the informal or
  neutral form is the present-day industry norm.

So the test is not "does a polite form exist" but "**is the polite form what apps
in that market actually use**". Where it is, the catalog uses it everywhere;
where it isn't, the catalog is consistent in the other direction and this
section says so. What the catalogs settled on:

| | | |
|---|---|---|
| ru, uk, cs | polite, infinitive chrome | already compliant |
| bg, BCMS | polite 2pl imperative | ~260 strings each converted from 2sg |
| de | `Sie` | 258 strings converted from `du` |
| tr | `siz` | 525 strings converted from `sen` |
| fr, pt, id, vi, hi, ja, ko | polite | already compliant |
| pl, es, it, zh | informal/neutral **by design** | consistent, left alone |

Two footnotes on that table. Chinese was the one catalog that used *both* forms
— 你 in 82 keys, 您 in 30 — so near-identical strings clashed
(`ChatFooter_YouBlockedUser` 您已屏蔽此用户 next to `PeerContact_BlockedCaption`
你已屏蔽此用户); the 30 were normalized to 你. And Turkish keeps the bare verb
stem on 17 toggle and radio labels (`Yazar adlarını renklendir`) because those
name a persistent setting rather than command the user — the same reasoning that
keeps the Russian infinitive.

`Push-to-talk` is the one place a 2sg imperative survives, because it is a
**product term**, not an instruction: BCMS `Pritisni i govori`, bg «Натисни и
говори», ru «Нажми и говори». Never politeness-fix a term.

### Join

English says "Join" for two unrelated actions, and a language that has a
membership verb will read the wrong one as nonsense on a call button:

- **Membership** — becoming a member of a Place or a chat, a state that outlives
  the click. `Common_Join`, `LeftPanel_JoinPlace`, `ChatFooter_JoinChat`,
  `ChatFooter_JoinPlace_Format`, `JoinRequest_*`.
- **Entering a live call** — walking into something already in progress and
  leaving again when it ends. `Call_Join`, `Call_JoinMuted`, `Call_JoinVideo`.

Most catalogs use one verb for both and are right to: pl `Dołącz`, cs
`Připojit se`, bg «Присъединете се», BCMS `Pridružite se`, de `Beitreten`, fr
`Rejoindre`, es `Unirse`, tr `Katılın`, ja 参加, ko 참여, zh 加入 all cover the two
senses the way English does.

East Slavic does not. Russian «Вступить» and Ukrainian «Вступити» mean *take up
membership* and nothing else, so on a call button they read as a mistranslation
even though a dictionary endorses them. Those two locales use the **enter** verb
for the call sense — ru «Войти», uk «Увійти» — and keep the membership verb for
`Common_Join` and friends. «Присоединиться» / «Приєднатися» is not wrong for a
call, but the catalog already said «Войти без звука», and one verb per action
beats two.

That split is why `Call_Join` exists as its own key instead of the call surfaces
reusing `Common_Join`. **A new call-context "Join" takes `Call_Join`; a new
membership one takes `Common_Join`.** Reusing the wrong one is invisible in
English and wrong in ru/uk.

### Cookies

**An HTTP cookie is a technical term, and must not be rendered as the food.**
«Печеньки», "kolačići", "biscotti" and friends are calques of the *snack*; a
reader looking for a cookie policy does not recognise them. Use whichever of
these the locale actually uses for the web technology:

- **The bare English term** where that is the norm: en, de, es, fr, pt, it, zh,
  ja, vi, id.
- **Native word for "files" + the Latin token `cookie`**, which is the house
  style across the Slavic catalogs: ru `Файлы cookie`, uk `Файли cookie`,
  pl `Pliki cookie`, cs `Soubory cookie`, bg `Файлове cookie`,
  bs/cnr `Cookie fajlovi`, hr `Cookie datoteke`, sr `Cookie фајлови`.
- **A transliteration** where the locale genuinely transliterates: ko `쿠키`,
  hi `कुकीज़`.

The test is "is this what people in that market actually call the web
technology", not "is there a native word for the biscuit". Turkish `Çerezler` is
literally "snacks" but *is* the established Turkish term for HTTP cookies —
that's the one case where the food word is correct, and it stays.

### Other shared terms

- **Member** — the person, not the abstract "membership": pl `uczestnik`,
  cs `člen`, bg `участник`, BCMS `član`, id `anggota`.
- **Push-to-talk** — translated, not left in English: pl `Naciśnij i mów`,
  cs `Stiskni a mluv`, bg `Натисни и говори`, BCMS `Pritisni i govori`,
  id `Tekan untuk bicara`.
- **Chat** — kept as `chat` where the locale borrows it (pl `czat`, BCMS Latin
  `chat`), but Serbian Cyrillic uses `чет` rather than leaving Latin text inside
  a Cyrillic sentence.
- **Register** — the polite second person, with the exceptions and the reasoning
  in [Register](#register).
- **Reveal** — an anonymous author revealing *themselves*, so the verb is
  reflexive wherever the language has that form: ru «Раскрыться», uk
  «Розкритися», pl `Ujawnij się`, cs `Odhalit se`, bg «Разкрийте се», BCMS
  `Otkrijte se`. A bare transitive "reveal" reads as revealing something else.
- **Copy** — one aspect per catalog. Every `*_Copy*` key uses the imperfective
  (ru «Копировать», uk «Копіювати», pl `Kopiuj`, cs `Kopírovat`); the perfective
  («Скопировать», `Skopiuj`, `Zkopírovat`) is equally correct Russian, Polish and
  Czech and equally wrong here, because two menus copying the same thing must not
  word it differently.
- **Mute** — an action on a button or menu entry, so a verb, and always about a
  *microphone* (`Call_MuteAll`, `Call_UnmuteAll`): ru «Отключить звук», not «Без
  звука». It never means leaving a call — that is `Call_HangUp`.

## Derived catalogs (BCMS)

Bosnian, Croatian, Montenegrin and Serbian are four standards of one language.
Translating them independently would produce four near-copies that drift apart
wherever a translator happened to word something differently — hiding the places
they genuinely differ. So **`bs` is the hand-written base** (ijekavian, Latin) and
`cnr`, `hr` and `sr` are generated from it by
[`scripts/derive-bcms.cmd`](../scripts/derive-bcms.cmd):

- `cnr` — Bosnian with Serbian-style month names and `-šć-` for `-št-`.
- `hr` — same ijekavian reflexes, different lexicon (`datoteka` not `fajl`,
  `sučelje` not `interfejs`) and wholly different month names (`siječanj`).
- `sr` — ijekavian → ekavian (`mjesto` → `mesto`), then Latin → Cyrillic.

**Edit `Strings.bs.json` / `Messages.bs.json` and re-run the script; never
hand-edit the derived files.** `scripts/derive-bcms.cmd --check` regenerates into
memory and fails if the files on disk disagree, which is what keeps that rule
enforceable.

Two traps the script encodes, worth knowing if you touch it:

- **`Date_*Pattern` values are format specifiers, not prose.** Transliterating
  `HH:mm` to `ХХ:мм` makes every timestamp unparseable, so those keys are copied
  through verbatim.
- **Brands and protocol words must survive transliteration** — `Windows`,
  `macOS`, `reCAPTCHA`, `API`, `cookie` and friends stay Latin, together with any
  case suffix glued to them (`Windowsu`, not `Wиндоwсу`).

## Derived Max catalog

`Max` is a deterministic pseudo-locale for finding UI that cannot accommodate the
widest shipped translation. It is not a language a user can select:

- `Languages.Max` has `LanguageSupport.None` and is absent from `Languages.All`,
  `Languages.AllUI`, `Languages.AllTranscription` and `Language.Parse`.
- Device detection, the account setting and the App-language picker cannot select it.
- Only an exact, case-insensitive `?ui-language=max` URL override activates it.
  Regional-looking values such as `max-US` are unsupported and resolve to English,
  like any other invalid authoritative override.
- An uncatalogued runtime message stays in its original English instead of being sent
  to AI translation with `Max` as a target language.

`Strings.max.json` and `Messages.max.json` are generated by
[`scripts/derive-max.cmd`](../scripts/derive-max.cmd). Never edit them by hand. For
each non-date key, the generator compares the value from every real UI catalog. A
plural value contributes every singular/few/many form independently, and the winner
is emitted as one form, so every count renders the same widest text.

The width score uses actual glyph advances from the checked-in regular TT Commons Pro
font. Combining marks have zero width; scripts not covered by that font use stable
Unicode-aware fallback widths, including full-width CJK and symbol glyphs. Placeholders
and markup do not affect the score because their rendered content is dynamic or
non-visible. The widest unbroken word is the tie-breaker after full line width.

All `Date_*` resources come from one existing locale so month/day names and format
patterns remain coherent. The generator chooses that locale from the widest month and
day name set; with the current catalogs, English wins. It does not splice date names or
format tokens across languages.

Generation is deliberately stable. `Max` does not rotate translations on a timer and
there are no random `M1`/`M2` variants, because either behavior would make screenshots
and visual-regression diffs nondeterministic. A separate word-pressure pseudo-locale can
be added later if browser testing shows that the full-line winner misses important
unbreakable-word failures.

Run derived generators in dependency order after changing a catalog:

```powershell
scripts/derive-bcms.cmd
scripts/derive-max.cmd
scripts/derive-bcms.cmd --check
scripts/derive-max.cmd --check
python -m unittest scripts/l10n/test_derive_max.py
```

## How it's enforced

| Test | What it guards |
|---|---|
| `AppLocalizationTest` | Every catalog defines exactly the English key set; every key is translated in every language and Max; placeholders survive translation; members and keys correspond 1:1; every member reads the key it's named after and resolves non-empty; plural form counts; `_Prefix`/`_Suffix` pairs; the two catalogs share no keys |
| `ServerErrorLocalizationTest` | Every `Error_*` key byte-matches a literal the code still throws, scanning `*.cs` only |
| `ValidationMessageLocalizationTest` | Both validation routes — BCL attributes reverse-matched through `MessageIndex`, and our own attributes reporting a key directly |
| `SystemEntryLocalizationTest` | Every `[Union]` system-entry kind is covered, so a new kind can't ship unlocalized |
| `FormSectionLocalizationTest` | A validation message renders with the section's `Label`, not the member name |
| `PluralLocalizerExtTest`, `DateFormatsLocalizerExtTest` | Form selection and the ICU-free `DateTimeFormatInfo` |
| `tests/ts/e2e/ui-localization-smoke.test.ts` | End-to-end: with each language selected, no visible text equals an English catalog value whose translation differs — and each screen shows *some* translated text, so a language that failed to apply can't pass vacuously |

`Validation_*` keys are excluded from the member-correspondence check: they are
resolved by key from `ActualChat.Core`, which can't reference `LocalizerExt`.

## Where the UI language comes from

**The account owns it.** `UserLanguageSettings.UILanguage` is a nullable
`Language` synced through `LanguageUI.Settings`, so changing it in one app
changes it in every app signed into the same account. `null` is not "unset" — it
is the **auto** selection, meaning "follow the device".

The first frame is resolved entirely from local startup inputs because the app has
to render before it can reach the server. The TypeScript `LocalizationUI` bootstrap
runs when `localization-ui.ts` loads, before Blazor exists, and creates its
`languageInfo` value from three inputs:

| Value | Where | What it is |
|---|---|---|
| `urlOverride` | `?ui-language=...` | a non-persistent forced language for this app instance |
| `selected` | `localStorage['ui.language']` | the cached account selection; `null` = auto |
| `clientLanguages` | `navigator.languages` | the device-language candidates used by auto |

That data rides to .NET in `BrowserInfo.InitResult` at no extra round trip.
`BrowserInfo` exposes it as `UILanguageOverride`, `StoredUILanguage` and
`ClientLanguages`, then `Languages.ResolveUILanguage` applies this exact priority:

1. If `UILanguageOverride` is present, resolve only that value.
2. Otherwise, use `StoredUILanguage` when it contains an explicit selection.
3. Otherwise, detect from `ClientLanguages`.

Device detection and ordinary URL overrides call `Languages.DetectUILanguage`, which
matches the primary ISO subtag against `Languages.AllUI`; `en-GB` and bare `en`
therefore land on the one English catalog. `?ui-language=<language>` accepts a full
locale or primary subtag (`de-DE`, `de-AT` and `de` all select German). The one special
case is exact `?ui-language=max`, which selects the hidden layout-testing catalog
described above without making Max detectable, parsable or account-selectable. An
override's presence is authoritative: an empty or unsupported value resolves to
`Languages.Main` (English) rather than falling through to the stored selection or
device detection. The URL value is never persisted.

The resolved `BrowserInfo.UILanguage` is copied once into the .NET
`LocalizationUI.Language` in `AppScopedServiceStarter.PrepareFirstRender`, right
after `BrowserInfo.WhenReady` and before anything of the app renders.
`LocalizationUI.Language` is a plain property rather than a state because
`AppStringLocalizer` reads it synchronously from ~1200 call sites. It never changes
for the lifetime of that app instance; a component that rendered before it was set
would stay English, which is why the copy happens before the first render.

The TypeScript bootstrap uses `localStorage`, not `LocalSettings`, so the cached
selection is available at bundle load and survives a session change. The TypeScript
class and its `window` global are both named `LocalizationUI`; `UILanguageInfo` is
the type of its `languageInfo` startup data contract.

**Changing it does not reload the app.** `LanguageUI`'s `SyncUILanguage` chain
watches `Settings.Computed.Changes` and does exactly one thing for each value: it
calls `SetStoredLanguage(settings.UILanguage)`, which delegates to
`window.LocalizationUI.set` and mirrors the account selection into the device
cache. Applying that selection is user-controlled: the running app keeps the
language selected at startup, and the cached choice takes effect only when the user
manually reloads or next starts the app. If `ui-language` remains in the URL, that
reload applies the override again; remove it before reloading to resume
account/device resolution. The same sync path handles local and remote account
changes because `Settings` is a `MutableState`, so its `Changes` fires locally too.

Do not confuse any of this with the *spoken*/transcription languages —
`Primary`/`Secondary`/`Tertiary` on the same record, and `GetChatLanguage` for
the per-chat override. Same service, two unrelated concepts.

**What is still English regardless:** Android permission dialogs and every OS
prompt. Push notification text is *not* on that list any more — it is composed on
the server in the recipient's language (#4125), which also covers the in-app
notification list, since both render the same `Notification.Text`. Neither is the
iOS share extension (#4261): it runs in its own process, so the app mirrors the
language it renders in into the App Group as `MauiPreferences.UILanguage`, and
`AppStrings.L` reads it there, falling back to `NSLocale.PreferredLanguages` until
the app has run once. See §3 and §4 of
[what's left](plans/localization-remaining.md).

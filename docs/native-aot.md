# Native AOT

## Overview

Native AOT compilation produces a single native executable with no JIT dependency.
This improves startup time, reduces memory usage, and is required for some platforms (e.g., iOS without interpreter).

We target Native AOT for MAUI apps on all platforms (Windows, Android, iOS).
The feature is opt-in via `UseNativeAot=true` in the build:

```bash
dotnet publish -c Release -f net10.0-windows10.0.22621.0 -p:UseNativeAot=true
```

Default builds use CoreCLR+R2R (Windows/Android) or Mono+interpreter (iOS) as before.

## Architecture

### CodeKeeper infrastructure (ActualLab.Fusion)

The `CodeKeeper` class prevents the ILC trimmer from removing types used via reflection.
It uses a dual mechanism:
- `[DynamicallyAccessedMembers(All)]` preserves metadata
- `typeof(T).GetMembers(...)` in a dead branch (`if (AlwaysFalse)`) forces ILC to generate native code

Key methods:
- `CodeKeeper.Keep<T>()` — retains a type (generic, compile-time known)
- `CodeKeeper.Keep(string assemblyQualifiedName)` — retains internal/inaccessible types by name
- `CodeKeeper.KeepSerializable<T>()` — retains a type plus its MemoryPack/MessagePack serializer wrappers

### AotSource / AotTypes (ActualChat)

Each assembly registers an `IAotSource` via a `[ModuleInitializer]` that populates `AotTypes`:

| Assembly | AotSource class | Module initializer |
|----------|----------------|-------------------|
| Core | `CoreAotSource` | `CoreSerializerAndRpcSetup` |
| Api | `ApiAotSource` | `ApiModuleInitializer` |
| Api.Contracts | `ApiContractsAotSource` | `ApiContractsModuleInitializer` |
| UI.Blazor | `BlazorUIAotSource` | `BlazorUIModuleInitializer` |
| UI.Blazor.App | `BlazorUIAppAotSource` | `BlazorUIAppModuleInitializer` |
| Maui | `MauiAotSource` | `MauiModuleInitializer` |
| App.Maui | `MauiAppAotSource` | `MauiAppModuleInitializer` |

Each AotSource has two parts:
1. **Generated partial** (`XxxAotSource.g.cs`) — auto-discovered types (components, APIs, serializables). Regenerated by `App.AotHelper -g`.
2. **Manual partial** (`XxxAotSource.cs`) — hand-coded `CodeKeeper.Keep<T>()` calls in a static constructor for types that can't be auto-discovered (DI services, framework internals, etc.)

### App.AotHelper

Console app that:
- **Generate mode** (`-g [project-root]`): discovers Blazor components (`ComponentBase` descendants), `IComputeService` API interfaces, and `[MemoryPackable]` serializable types across all ActualChat assemblies. Outputs `XxxAotSource.g.cs` files into each target project. Run via `run-aot-type-generator.cmd` at the project root.
- **Test mode** (no args): validates all registered types can be loaded, instantiated, and reflected upon. Uses `IAotTester` implementations (`ComponentTester`, `ApiTester`, `SerializableTester`).

The App.AotHelper project itself is configured for Native AOT publishing (`PublishAot=true` in Release) to serve as a smoke test.

### MessagePack formatter discovery

For each serializable root type in a target assembly, `MessagePackFormatterDiscovery` walks the full reachable type graph — array elements, `Nullable<T>` underlying types, generic arguments, base type, generic interface arguments, and serialized properties/fields — and collects every concrete MessagePack formatter needed to deserialize that graph:
- `[MessagePackFormatter(typeof(X))]` attributes are read directly; if `X` is an open generic with one parameter, it is also closed over the decorated type (catches e.g. `StringIdentifierMessagePackFormatter<ChatId>` for all ~30 identifier types).
- Each reachable type is resolved via `DefaultMessagePackResolver.Instance.GetFormatter<T>()` (invoked via reflection) to obtain the concrete formatter that MessagePack would pick at runtime. This catches `GenericEnumFormatter<TEnum>`, `ArrayFormatter<T>`, `NullableFormatter<T>`, `InterfaceImmutableDictionaryFormatter<K,V>`, `UnitMessagePackFormatter`, `ApiArrayMessagePackFormatter<T>`, and so on.

Formatters are filtered to the `MessagePack.*`, `ActualLab.*`, `ActualChat.*` assembly prefixes (runtime-emitted formatters from `DynamicObjectResolver+` cannot be named by AQN) and emitted into the per-assembly `XxxAotSource.g.cs` as `CodeKeeper.Keep("<AQN>")` calls. Walking bases + generic interface arguments is required to reach types that appear only in a command's declared interface (e.g. `Unit` in `ISessionCommand<Unit>`).

### System.Text.Json source generation

`BlazorUIJsonContext` and `BlazorUIAppJsonContext` provide source-generated JSON metadata for types used in JS interop (return types from `InvokeAsync<T>`, parameter types in `[JSInvokable]` methods).

Registered via `AotJsonContexts.Add(...)` in module initializers.

**Current status**: These contexts are registered but **not injected** into `IJSRuntime`'s `JsonSerializerOptions`. Attempts to inject them (via `InjectJsonTypeInfoResolvers`) cause `object[]` serialization failures in Blazor's internal IPC, even when wrapped in a `SafeCompositeResolver` that returns null for unknown types. The mere presence of a custom resolver in the `TypeInfoResolverChain` changes how STJ resolves types like `object[]` used internally by JSRuntime.

Instead, STJ AOT compatibility is achieved via `CodeKeeper.Keep(string)` calls that retain the internal STJ converter types (like `EnumConverter<T>`, `ArrayConverter<T[], T>`, `ObjectDefaultConverter<T>`, `SmallObjectWithParameterizedConstructorConverter<...>`, etc.) by their assembly-qualified names. This is done in `BlazorUIModuleInitializer.KeepBlazorIpcTypes()`.

**TODO**: Investigate whether `JsonSerializerIsReflectionEnabledByDefault=false` works with just the CodeKeeper approach, or if source-gen context injection is needed for full AOT without reflection. May require a custom `IJSRuntime` wrapper that uses our contexts directly instead of going through the `TypeInfoResolverChain`.

## Current status (2026-04-04)

### What works

- **Windows Native AOT MAUI app** starts, shows window, loads Blazor UI, connects to RPC, renders chat list and messages
- **App.AotHelper** validates 906+ types (610 components, 42 APIs, 254 serializables) in both JIT and AOT modes
- **Build configuration**: `UseNativeAot` property in `App.Maui.csproj` (default: false) switches between CoreCLR/R2R and Native AOT for all platforms
- **Warning suppressions**: All IL trimming/AOT warnings suppressed globally in `Directory.Build.props`
- **DynamicDependency cleanup**: All `[DynamicDependency]` attributes replaced with CodeKeeper patterns in AotSource files

### Known issues

1. **STJ context injection**: Source-generated JSON contexts can't be injected into JSRuntime's resolver chain (see above). CodeKeeper string-based keeps work as a substitute.

2. **WindowConfigurator**: `window.GetAppWindow()` fails in unpackaged mode (`WindowsPackageType=None` required for AOT). Protected with try/catch, falls back to `window.Activate()`.

3. **WindowsAppIconBadge**: `CreateBadgeUpdaterForApplication` fails without AppxManifest.xml in unpackaged mode. Non-blocking FCE.

4. **MissingTemplateException**: A few opaque "Template is missing" errors from `Internal.Runtime.TypeLoader` — no stack traces available to diagnose. Non-blocking.

5. **Binary size**: ~120MB native executable (Windows x64). No size optimization done yet.

### Remaining STJ converter types to keep

When new types are used in JS interop, their STJ converters may need manual `CodeKeeper.Keep(string)` entries in `BlazorUIModuleInitializer.KeepBlazorIpcTypes()`. Common patterns:

- **Enums**: `EnumConverter<T>` — needed for any enum passed through JS interop
- **Value-type arrays**: `ArrayConverter<T[], T>` — for arrays of value types or custom structs
- **Parameterized constructors**: `SmallObjectWithParameterizedConstructorConverter<...>` — for records/structs with constructor parameters (like `Range<T>`, `KeyValuePair<K,V>`)
- **Collection interfaces**: `IEnumerableOfTConverter`, `ICollectionOfTConverter`, `IDictionaryOfTKeyTValueConverter`, etc. — for collection properties
- **Property metadata**: `JsonPropertyInfo<T>` — for types used as properties of other serialized types
- **Object converters**: `ObjectDefaultConverter<T>` — for reference types with default serialization

### Platform-specific notes

**Windows**: Requires `WindowsPackageType=None` for unpackaged deployment. MSIX packaging not supported with Native AOT.

**Android**: `PublishAot=true` replaces CoreCLR+R2R. Not yet tested.

**iOS**: `PublishAot=true` replaces Mono+interpreter. Not yet tested. iOS already uses AOT (Mono AOT), so Native AOT is a different compilation path.

# AI image suggestions

## Goal

A group chat created without a picture shows a generated letter-avatar forever,
because setting a real one is a deliberate act nobody performs. Offer one
instead: when an owner opens such a chat, a banner appears with an image already
generated for *that* chat, and two buttons — **Upload** (the existing picker) and
**Regenerate** (a modal showing the image description, which the owner can edit).
Accepting the suggestion sets the chat picture.

The picture is the first consumer, not the point. The point is a generation and
suggestion service general enough that place pictures, place backgrounds and
custom emoji — all already in the [backlog](./index.md#chat--messaging) — reuse
it without reopening its design.

## Scope

In: the generator, the suggestion store, the chat-picture consumer, the banner.

Out, deliberately: the post-creation "open the chat in edit mode" flow, making
the `<Pic>` in the settings modals clickable, place pictures and backgrounds,
user-avatar generation. Each is a separate change that this one does not block.

Adjacent, and probably its own plan: the **internal chat description** the image
prompt is written from. See [Prompt authoring](#prompt-authoring).

Nothing in the codebase generates images today, and nothing addresses "one
pending suggested image for a thing". Those are the two new pieces.

### Placement of what's new

Every new component here is deliberately placed for reuse rather than beside its
first caller:

- **`IImageGenerator`** → `ActualChat.Core.Server`, in `AI/`, namespace
  `ActualChat.AI`, next to the existing provider-agnostic AI primitives. No chat,
  media or UI dependency. Local alternative (putting it in `Media.Service`)
  rejected: emoji generation will not go through the media suggestion path, and a
  provider seam belongs with the other provider seams.
- **`IImageSuggestionsBackend`** → contract in `ActualChat.Media.Contracts`,
  implementation in `Media.Service`. It owns generated media, so it belongs with
  the service that owns media. Keyed by an opaque string — it never learns what a
  chat is.
- **`IImageSuggestions`** (client-facing) → contract in
  `ActualChat.Api.Contracts`, implementation in `Chat.Service`. Deliberately
  *not* generic; see [Why the client API is not generic](#why-the-client-api-is-not-generic).
- **`ChatImageDescriber`** → `ActualChat.Chat.ML`, beside the other LLM-backed
  extractors. Chat-specific by nature.
- **Prompt template** → `ActualChat.configs` repo,
  `prompts/suggest-image-description.md`, reached through
  `CoreServerSettings.PromptsDir`. Same as every other prompt; it is not in this
  repo.

## The three layers

```
IImageSuggestions          (Api.Contracts → Chat.Service)
  session-scoped, per-target, permission-checked
  composes the backend key; writes the image description
        │
        ▼
IImageSuggestionsBackend   (Media.Contracts → Media.Service)
  keyed by an opaque string
  moderation → generation → media save → row swap; dismissal
        │
        ▼
IImageGenerator            (Core.Server/AI)
  provider-agnostic text → bytes
```

Each layer knows only the one below it. The chat layer knows nothing about
Cloudflare; the generator knows nothing about chats, media or sessions; the
suggestion store knows nothing about either.

### Layer 1 — `IImageGenerator`

```csharp
namespace ActualChat.AI;

public interface IImageGenerator
{
    Task<GeneratedImage> Generate(ImageGenerationRequest request, CancellationToken cancellationToken);
}

public sealed record ImageGenerationRequest(string Prompt)
{
    public int Width { get; init; } = 512;
    public int Height { get; init; } = 512;
    public long? Seed { get; init; }
    // Empty today; present so image-to-image doesn't force a signature change.
    public ApiArray<ReadOnlyMemory<byte>> InputImages { get; init; }
}

public sealed record GeneratedImage(string ContentType, int Width, int Height, byte[] Data);
```

`CloudflareImageGenerator` is the first implementation:
`@cf/black-forest-labs/flux-2-klein-4b`, plain REST from `HttpClient`, no Worker
script. Two integration facts worth writing down because they are not guessable:

- The FLUX.2 models require **`multipart/form-data` even for a text-only
  prompt**. Only `flux-1-schnell` takes JSON, and it has no size parameter at
  all — it is fixed at 1024×1024.
- The response is the standard Cloudflare v4 envelope with the image as a base64
  string in `result.image`.

Settings land on `CoreServerSettings`: `CloudflareAccountId`, `CloudflareAiToken`,
`ImageGeneratorModel`. When the token is empty the module registers a stub that
reports "unavailable", matching how `IsSummarizationEnabled` gates the
summarizers — no host is required to configure this.

Rate limiting mirrors the LLM path: a decorator over `IImageGenerator` backed by
the existing `RedisTokenBucketRateLimiter`, so a runaway caller cannot drain the
account. Every call gets a `CoreServerInstruments.ActivitySource` span.

### Layer 2 — `IImageSuggestionsBackend`

One pending suggestion per key. Generating a new one replaces and deletes the
old.

```csharp
namespace ActualChat.Media;

public interface IImageSuggestionsBackend : IComputeService, IBackendService
{
    // Returns null while the suggestion is dismissed - see GetDismissedUntil
    [ComputeMethod]
    Task<ImageSuggestion?> Get(string key, CancellationToken cancellationToken);
    [ComputeMethod]
    Task<Moment?> GetDismissedUntil(string key, CancellationToken cancellationToken);

    [CommandHandler]
    Task<ImageSuggestion?> OnGenerate(ImageSuggestionsBackend_Generate command, CancellationToken cancellationToken);
    [CommandHandler]
    Task OnDismiss(ImageSuggestionsBackend_Dismiss command, CancellationToken cancellationToken);
    [CommandHandler]
    Task OnRemove(ImageSuggestionsBackend_Remove command, CancellationToken cancellationToken);
}
```

#### The key

An opaque string, composed by the caller. It encodes whatever the caller needs to
distinguish one suggestion from another — the target's id, which image of that
target it is, and anything a future consumer decides to add. For a chat picture:

```
picture/c:abcdefghij
```

Keeping it a string rather than a typed pair is a deliberate choice with three
payoffs. It removes any dependency on [PR #4534](#on-4534) from this contract.
It lets the composition change — adding a user segment, a variant index, a
version — without a wire-format change, because nothing below the client layer
parses it. And it matches how `FlowId` already works in this codebase: a
`"{name}:{arguments}"` string whose arguments are free-form and parsed only by
the flow that owns them.

If it earns structure later, `ImageSuggestionKey` becomes a
`ISymbolIdentifier`-style readonly struct with `Parse`/`Format`, exactly as
`FlowId` is, and the stored strings stay valid.

#### `ImageSuggestionsBackend_Generate`

This is the command that does the work, so it is worth spelling out.

```csharp
[DataContract, MessagePackObject]
public sealed partial record ImageSuggestionsBackend_Generate(
    [property: DataMember, Key(0)] string Key,
    [property: DataMember, Key(1)] string ImageDescription
) : ICommand<ImageSuggestion?>, IBackendCommand, IHasShardKey<string>
{
    [DataMember, Key(2)] public int Width { get; init; } = 512;
    [DataMember, Key(3)] public int Height { get; init; } = 512;
    [DataMember, Key(4)] public MediaKind MediaKind { get; init; } = MediaKind.ChatPicture;
    // Set by a regenerate so two owners racing don't both replace the same row
    [DataMember, Key(5)] public long? ExpectedVersion { get; init; }

    [JsonIgnore, Newtonsoft.Json.JsonIgnore, IgnoreDataMember, IgnoreMember]
    public string ShardKey => Key;
}
```

`ImageDescription` is a description of the *picture*, not of the chat — the
client layer has already done that translation. The backend never calls an LLM.

What `OnGenerate` does, in order:

1. **Read the current row** for `Key`. If `ExpectedVersion` is set and doesn't
   match, return the current suggestion unchanged — another owner won the race
   and their image is on screen.
2. **Screen the description** with `@cf/meta/llama-guard-3-8b`. A refusal returns
   `null`; the caller renders "couldn't come up with one".
3. **Wrap it in the style template.** The description supplies the subject; the
   visual style is ours, so every generated chat icon looks like it belongs to
   the same app. Short descriptions get padded with descriptive context, which
   measurably reduces the provider's false-positive rejections.
4. **Call `IImageGenerator.Generate`.** A provider NSFW rejection is an ordinary
   outcome: return `null`, log at `Debug`, do not throw. So is a rate-limit or
   capacity error, which the caller may retry.
5. **Process and save the bytes** — `MediaProcessor.ProcessUpload(file,
   MediaKind, …)` then `MediaSaver.Save(MediaId.New(…), processed, isUpdate:
   false, MediaKind, …)`. This is the path `AvatarPicturesController` uses.
6. **Write the row and delete the previous one's media** in the same operation,
   so a suggestion never outlives the media it points at and vice versa.
7. **Clear any dismissal.** A freshly generated suggestion is a new offer.

Failures at steps 2 and 4 are the expected ones and all return `null`. Failure
after step 5 leaves a saved `Media` with no row; the sweep in
[Storage](#storage) collects it.

#### Dismissal

`OnDismiss` stores a **moment**, not a flag: `DismissedUntil`. A chat that still
has no picture in a month is a chat that should be offered one again, so
dismissal expires. The default is 30 days; the command can carry an explicit
moment for "not now" versus "never" (the latter being a far-future date rather
than a separate column).

`Get` returns `null` while `DismissedUntil` is in the future, so the common
caller needs one call and cannot forget the check. `GetDismissedUntil` exposes
the date for a caller that wants to say *when* it will come back, or to show the
suggestion somewhere the banner is suppressed.

**Dismissal is stored against the key, so by default it is shared by everyone who
can act on that content** — one owner dismissing it dismisses it for all of them.
That is a real behavioural choice and the opposite of how `AddChatMembersBanner`
works. It is defensible here because the *suggestion* is shared too: there is one
pending image per chat, not one per owner, so "we don't want an AI picture for
this chat" reads as a property of the chat. Because the key is opaque, making it
per-user instead is a one-line change at the composition site (`picture/c:…/u:…`)
and no change at all below it. See [Open questions](#open-questions).

#### `ImageSuggestion`

```csharp
[DataContract, MessagePackObject]
public sealed partial record ImageSuggestion(
    [property: DataMember, Key(0)] string Key,
    [property: DataMember, Key(1)] MediaId MediaId,
    [property: DataMember, Key(2)] string ImageDescription,
    [property: DataMember, Key(3)] Moment CreatedAt,
    [property: DataMember, Key(4)] long Version = 0
) : IHasVersion<long>
{
    // Populated on read only, like Chat.Picture
    [DataMember, Key(5)] public Media? Media { get; init; }
}
```

`ImageDescription` is carried because Regenerate has to show it for editing.

**The backend performs no permission check** — consistent with every other
`*Backend` here, and with `IContentLinksBackend`, which resolves any content
reference without a `Session`. Authorization is the client layer's job, which is
why that layer is shaped the way it is.

### Layer 3 — the client-facing API

```csharp
namespace ActualChat.Chat;

public interface IImageSuggestions : IComputeService
{
    [ComputeMethod]
    Task<ImageSuggestion?> GetForChat(
        Session session, ChatId chatId, ImageSlot slot, CancellationToken cancellationToken);
    [ComputeMethod]
    Task<Moment?> GetDismissedUntilForChat(
        Session session, ChatId chatId, ImageSlot slot, CancellationToken cancellationToken);

    [CommandHandler]
    Task<ImageSuggestion?> OnGenerateForChat(
        ImageSuggestions_GenerateForChat command, CancellationToken cancellationToken);
    [CommandHandler]
    Task OnAcceptForChat(ImageSuggestions_AcceptForChat command, CancellationToken cancellationToken);
    [CommandHandler]
    Task OnDismissForChat(ImageSuggestions_DismissForChat command, CancellationToken cancellationToken);
}

public enum ImageSlot { Picture = 0, Background = 1 }

[DataContract, MessagePackObject]
public sealed partial record ImageSuggestions_GenerateForChat(
    [property: DataMember, Key(0)] Session Session,
    [property: DataMember, Key(1)] ChatId ChatId,
    [property: DataMember, Key(2)] ImageSlot Slot,
    // null = write a fresh description from the chat; non-null = the owner's edit
    [property: DataMember, Key(3)] string? ImageDescription
) : ISessionCommand<ImageSuggestion?>;
```

`ImageSlot` lives here, at the client layer, because it is part of how a *caller*
names its images — a chat has a picture, a place has a picture and a background.
The backend only sees the composed string.

`OnGenerateForChat` requires `CanEditProperties()` on the chat's rules, asks
`ChatImageDescriber` for a description when none was supplied, composes the key,
and calls `ImageSuggestionsBackend_Generate`.

`OnAcceptForChat` re-checks the rules, runs `Chats_Change` with `ChatDiff.MediaId`
set, then `ImageSuggestionsBackend_Remove` with `mustDeleteMedia: false` — the
media is now the chat's picture and must survive.

`OnDismissForChat` checks the rules and delegates to
`ImageSuggestionsBackend_Dismiss`.

#### Why the client API is not generic

A generic `Get(Session, string key)` would be one method instead of five per
target, and it is the wrong trade. Generation costs money and calls an external
provider; an endpoint taking a caller-supplied key is an endpoint whose
authorization is a `switch` that must stay exhaustive forever, and whose failure
mode when it isn't is a stranger burning credits against content they cannot see.
Per-target methods make the permission check unavoidable at the call site and let
each target use the check it actually needs — `CanEditProperties()` for a chat,
something else for a place. Adding places later costs five methods; that is cheap
insurance.

## Storage

A new table in `MediaDbContext`, so the suggestion and the media it points at
commit and delete together:

```
_ImageSuggestions
  key               text PK     -- "picture/c:abcdefghij"
  media_id          text NULL   -- null when only a dismissal is recorded
  image_description text
  created_at        timestamptz
  dismissed_until   timestamptz NULL
  version           bigint      -- [ConcurrencyCheck]
```

A dismissal with no suggestion is a valid row, which is how "dismissed, nothing
generated yet" is represented.

Redis was the alternative and is rejected: the generated image is a durable
`Media` row plus a blob, so losing the pointer leaks both. One table keeps the
pair recoverable and lets a sweep find what to collect.

**Orphan risk is real and bounded.** A suggestion generated for a chat whose
owner never returns holds one ~50 KB blob indefinitely. Mitigation: accepting or
dismissing resolves it immediately, and a periodic sweep removes rows whose
`created_at` is older than 30 days and whose media is not referenced. The
upload-session lifecycle added in `688e10f12d` — releasing reserved media when a
draft is discarded — is the precedent.

## Prompt authoring

Generation is **two LLM-free-of-each-other steps**, and the owner edits the
second one's input:

```
chat (title, description, recent content)
   │  [1] ChatImageDescriber - OpenAI, prompts/suggest-image-description.md
   ▼
image description   ← this is what the Regenerate modal shows and lets you edit
   │  [2] style template + moderation + FLUX
   ▼
image
```

Step 1 is `ChatImageDescriber` in `Chat.ML`, modelled on
`ThreadInsightExtractor`: render the template with the chat's material, read back
`<image_description>`, catch and return empty. Step 2 is the backend's, described
above. Splitting them is what makes the edit affordance work — the owner adjusts
a sentence about a picture, not a sentence about a chat.

### The internal chat description — an open dependency

Feeding step 1 raw recent entries is the cheap version and is what this plan
assumes to ship. The better input is a maintained **internal description of the
chat**: an LLM-written account of what this chat is actually about, updated over
time, never shown to users and therefore not a field on `Chat`.

Its natural storage is **chat-scoped KVAS** (`c/{chatId}/`, as `ChatPinnedEntries`
already uses) — a typed record under a key, shared per chat, no migration. That
answers "somewhere to put ML-related data keyed by an object" without inventing a
store.

Its natural cadence is decreasing: frequent while a chat is new and its character
is still forming, rarer once it has settled, with a new message able to bring the
next update forward. `PeriodicFlow` already has exactly this contract — `Run()`
returns the moment it next wants to wake, and `Moment.MaxValue` means never
again — so an adaptive backoff is a return value, not new machinery.

**Before building that, the reuse question needs answering.** This codebase
already summarizes chats three ways: `ConversationsBackend` produces a
`ConversationSummary(Title, Description, Summary)` per conversation,
`ChatDigestSummarizer` summarizes the last 24 hours for the email digest, and
`ThreadInsightExtractor` writes a title and description for a thread. An internal
chat description may well be an *aggregation of recent conversation summaries*
rather than a fourth independent summarizer over raw entries — cheaper, already
incremental, and already maintained by a flow. That deserves its own plan and
should not be settled inside this one.

Consequently: **this plan ships step 1 reading title, description and a truncated
window of recent non-system entries via `IChatDialogFormatter`**, and swaps its
input for the internal description when that lands. The interface does not
change.

## Moderation

**This is the single largest risk in the design, and it is a platform constraint
we cannot configure away.** Workers AI applies an undocumented, non-disableable
NSFW filter to the FLUX models, returning an error code that is not in
Cloudflare's published error table. It is badly calibrated — reported false
positives include the word *hamburger* and *"a man in his late 50s wearing a
suit"*. The opt-out request ([cloudflare/developer-platform#58]) has been open
since May 2026 with no maintainer response.

Three consequences, all reflected above:

1. **The rejection is an ordinary outcome, not an exception** — step 4 of
   `OnGenerate` returns `null` and nothing logs above `Debug`.
2. **Raw user text never reaches the image model** — the owner's edited
   description is screened with `@cf/meta/llama-guard-3-8b` and substituted into
   the style template as a subject phrase.
3. **Prototype before building.** Fifty realistic chat titles through the real
   endpoint, counting rejections, is an afternoon and decides whether the feature
   is viable. If the rate is bad the fallback is not another Workers AI model —
   the filter is platform-side — but the partner-routed
   `black-forest-labs/flux-2-pro-preview`, which exposes a tunable
   `safety_tolerance` at roughly 100× the unit cost.

Output moderation does not exist: Cloudflare's own AI Gateway Guardrails evaluate
text only and explicitly do not inspect generated images.

## The banner

`ChatPictureSuggestionBanner`, copied from `AddChatMembersBanner`. It renders
when all of these hold:

- the chat is a group or place chat, not a thread and not a peer chat;
- `chat.MediaId.IsNone` — no real picture has ever been set;
- `Rules.CanEditProperties()`;
- `GetDismissedUntilForChat` is null or in the past.

On first render with no stored suggestion it issues `GenerateForChat` once and
shows a skeleton until the compute method invalidates. Two owners opening the
chat simultaneously can each trigger a generation; `ExpectedVersion` makes the
second a no-op and the wasted image costs $0.0003. That is cheaper than a
distributed lock.

Buttons: **Upload** opens `ImageCropPicker` exactly as the settings modal does
today. **Regenerate** opens a small modal showing the image description as
editable text with a Generate button. Accepting is clicking the suggested image
itself.

Note that no dismissal state lives in `LocalSettings` or user KVAS — it is in the
suggestion row. The banner reads it through `GetDismissedUntilForChat` like any
other server state.

## Cost

At 512×512 on `flux-2-klein-4b` a generation is one 512px tile, 26.05 neurons,
**$0.000287** — about 35 images per cent. The free allocation of 10,000
neurons/day covers ~384 images, which is all of dev and staging. Cloudflare bills
in tiles, so 256 and 128 cost the same as 512 and 1024 costs four times as much;
generating at 512 and letting the image proxy serve a 128px icon is the right
default. Replicate and fal round up to a whole megapixel, so the same avatar
bills at full-MP rates there — the tile billing is why this provider wins for
this workload rather than the headline rate.

`flux-2-klein-4b` is **Apache 2.0**, which removes the licensing question
entirely. The 9B and `dev` variants are under the FLUX non-commercial licence;
staying on 4B is partly a licensing decision, not only a cost one.

## On #4534

The earlier draft of this plan keyed the backend on `(ContentRef, ImageSlot)`,
which made it depend on [PR #4534](https://github.com/Actual-Chat/actual-chat/pull/4534)
— a draft that replaces the concrete `ContentId` on `dev` with an abstract base
of the same name and introduces `ContentRef`.

The opaque string key removes that dependency. The client layer composes
`"picture/c:abcdefghij"` today using `ChatId.Value`, and can switch to
`chatId.ContentRef.Value` when #4534 lands, with no contract change and no
migration beyond a key rewrite if the prefix changes. Nothing in this plan now
blocks on that PR.

## Open questions

1. **Shared or per-user dismissal.** Stored against the key, dismissal is shared
   by all owners. Adding a user segment to the key makes it per-user. Which is
   right depends on whether "no AI picture here" is a chat decision or a personal
   one.
2. **Accept gesture.** Clicking the image is assumed. A separate "Use this"
   button is the alternative; clicking an image to commit a change is not a
   pattern used elsewhere in this UI.
3. **Generate budget.** No cap is specified. A per-chat daily limit is cheap
   insurance against an owner discovering the button is fun.
4. **Chats that once had a picture and lost it.** `MediaId.IsNone` is true for
   both "never set" and "cleared". Treating them the same re-offers a suggestion
   to someone who deliberately removed one.
5. **The internal chat description** — its own plan, and specifically whether it
   aggregates existing conversation summaries or summarizes raw entries afresh.

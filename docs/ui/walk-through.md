# UI walk-through

This is a route map of the Voxt UI: every screen, panel, menu, modal, overlay
and transient surface, in the order you can walk them, together with the
localization keys each one renders.

It exists for two jobs:

- **Reviewing a translation in context.** Pick a key group from the
  [coverage table](#coverage-table), follow the stop it points at, read the
  string where a user actually reads it.
- **Layout testing.** Walk the whole thing with
  [`?ui-language=max`](#the-max-pseudo-locale) and the UI renders the *widest*
  translation of every string at once. Anything that cannot accommodate real
  translations breaks visibly. The findings from the first such pass are in
  [Max-locale layout findings](../plans/max-locale-findings.md).

::: info Scope
Every key in `Strings.*.json` and `Messages.*.json` is covered **except the
`Error_*` group** (113 keys). Those are raised as exceptions and localized at
render time; see
[i18n.md &rarr; Errors and server messages](../i18n.md#errors-and-server-messages).
:::

## The Max pseudo-locale

`Max` is a hidden, generated catalog. For every key it holds the **visually
widest** of the 22 shipped translations, measured with real TT Commons Pro
glyph advances. It is not a language: it is the worst case all 22 languages can
put on a layout, in one pass.

| | |
|---|---|
| Activate | `?ui-language=max` &mdash; exact, case-insensitive, URL only |
| Persisted | No. Never written to the account or `localStorage` |
| Selectable | No. Absent from the App-language picker, device detection and `Language.Parse` |
| Generated by | [`scripts/derive-max.cmd`](https://github.com/Actual-Chat/actual-chat/blob/main/scripts/derive-max.cmd) &mdash; never edit `Strings.max.json` by hand |
| Stability | Deterministic. No rotation, no random variants, so screenshots diff cleanly |

Full rules: [i18n.md &rarr; Derived Max catalog](../i18n.md#derived-max-catalog).

**How much pressure it applies.** Against English, measured over 1348 keys:

| percentile | width vs English |
|---|---|
| median | 1.62x |
| p75 | 1.94x |
| p90 | 2.37x |
| p99 | 4.20x |

Short labels are the worst offenders in relative terms &mdash; `Off` &rarr;
`Desactivado` (3.98x), `All` &rarr; `Wszystkie` (3.97x), `Join` &rarr;
`Присоединиться` (4.10x) &mdash; which is exactly why tab strips, toggles and
compact buttons are the first things to fail.

::: warning Start at `/chat`, not `/`
`/` redirects a signed-in user to `/chat` and the redirect drops the query
string. The running instance keeps Max (the TypeScript bootstrap read the
parameter before the redirect), but the address bar no longer has it, so a
refresh silently reverts to your account language. Always open
`/chat?ui-language=max`.
:::

Max survives in-app navigation for the life of the app instance &mdash;
`LocalizationUI.Language` is set once before the first render and never changes.
Any **full page load** re-reads the URL, so keep `?ui-language=max` on every
address you type.

## Setup

```bash
# server (host): ./run-watch.cmd, or /server-start
# browser (host): ai chrome        -> Chrome with CDP on :9222
```

Sign in and clear the first-run surfaces so they don't block the walk:

```js
await debugUI.signIn('+1 555 555 5550');
debugUI.resetOnboarding(false);   // skip onboarding
debugUI.resetBubbles(false);      // skip feature tips
```

Re-enable them with `true` when you reach [stop 2](#_2-onboarding) and
[stop 3](#_3-feature-bubbles).

**Viewports to walk.** The app has one layout switch: `ScreenSize.Small`
("narrow") below the `md` breakpoint &mdash;
`(min-width: 820px) and (pointer: fine)` or `min-width: 1100px`. Walk at least
these four:

| Viewport | Why |
|---|---|
| 390 x 844 | iPhone 13/14 &mdash; the smallest phone worth supporting |
| 820 x 720 | narrowest *wide* layout; left + right panels compete hardest |
| 1280 x 800 | smallest reasonable desktop |
| 1440 x 900 | reference desktop |

From the chrome-devtools MCP, `emulate` with
`viewport: "390x844x3,mobile,touch"` gives a true 390 px viewport;
`resize_page` cannot go below the OS window minimum (~500 px on Windows).

Recording bills speech recognition per second. Turn it off the moment the
check is done; see the `/debug-ui` skill.
:::

**Setting up the two-user session.** `Call_*` and half of `Video_*` only render
when someone else is in the call, so this needs two browsers
(`ai chrome*2` &rarr; `mcp__chrome1__*` / `mcp__chrome2__*`):

```js
// chrome1
await debugUI.signIn('+1 555 555 5550');
// chrome2
await debugUI.signIn('+1 555 555 5551');
// both -> the same chat, then chrome1 clicks the record button,
// then the camera icon -> "Start video"
```

Two traps that cost a pass each:

- **Use a group chat both users belong to, not a peer chat.** In a peer chat
  with someone who is not yet in your contacts, the footer renders without the
  record button at all &mdash; there is nothing to click.
- **The joiner's surfaces live in the chat header,** not in a modal:
  `Call_JoinMuted` appears as a pill in user B's header the moment user A
  starts streaming. That is where
  [M10](../plans/max-locale-findings.md#m10--the-join-muted-call-to-action-is-cut-mid-word)
  hides.

## Never localized

These render English in every language, **by design**. Seeing English here
during a Max walk is correct, not a bug. Full rationale in
[i18n.md](../i18n.md).

- **Landing pages and legal docs** &mdash; `Pages/Landing/`, `/docs/privacy`,
  `/docs/terms`, `/docs/faq`, `/docs/cookies`
- **Diagnostics panels** &mdash; `VideoDiagnosticsModal`,
  `AudioDiagnosticsModal`, `LogView` output (~165 technical labels; the *entry
  points* into them are localized)
- **Brand and product names** &mdash; `GIF`, `Google Play`, `App Store`,
  `Microsoft Store`, `KLIPY`, `Sentry`, `Firebase Analytics`, `Live Activities`
- **`DELETE`** in the delete-account modal &mdash; it is compared against typed
  input
- **Developer surfaces** &mdash; every `/test/*` page, admin menus, the
  fake-reCAPTCHA branch, `EnableIncompleteUI` mockups, `/test/discover`
- **`Date_*Pattern` values** &mdash; `HH:mm` and friends are format specifiers
- **`alt` attributes naming an asset** &mdash; `Web/Chrome/01`,
  `Tutorial slide #1`

::: tip English under Max is not always an exception
Max holds the *widest* translation, and for some keys that is English. A Max
walk showing `Notifications panel` in English can simply mean English is the
widest of the 22. Check `Strings.max.json` before filing it.
:::

## Reachable only outside the browser

Not walkable in a web session &mdash; needs a device or the native app:

- Push notification text &mdash; composed on the server, English regardless
- The iOS share extension, Android permission dialogs, every OS prompt
- `NativeApp_*` &mdash; Windows auto-start policy strings (MAUI on Windows only)
- `Ptt_*` in full &mdash; push-to-talk is a device feature; the web shows an
  admin-only preview on local hosts
- The native-only rows of Settings &rarr; Permissions
  (`Permission_LockScreenCalls`, `Permission_LiveActivities`,
  `Permission_BackgroundActivity`, `Permission_Contacts`)

## Automating the walk

A layout pass is much faster with a DOM scanner than with eyes. The one used
for [the first Max audit](../plans/max-locale-findings.md) reports four things per
screen, and is ~120 lines of plain JS you paste through
`mcp__chrome1__evaluate_script`:

| Check | What it catches |
|---|---|
| `clipped-x` | `overflow: hidden` with no `text-overflow: ellipsis` &mdash; text hard-cut |
| `child-clipped-by-parent` | a child's box extends past a clipping parent |
| `past-viewport-right/left` | anything pushed outside the viewport |
| text-node collision | two pieces of text painted on top of each other |

Two refinements matter or the output is unusable noise:

1. **Scope to the top layer.** Pass a `root` selector (`.modal-overlay` when a
   modal is open) &mdash; otherwise the page behind the modal dominates the
   report.
2. **Discount intentional overlaps &mdash; but only the scrolling kind.** A
   sticky header painted over scrolling content is not a bug. Skip a text
   collision only when the *back* element sits in a scroll container the
   *front* element is outside of, so the back text can move out from under it.

   Do **not** skip a collision just because the front element is absolutely
   positioned, has a z-index or has an opaque background &mdash; an
   always-visible overlay sitting on a static sibling is exactly the bug you
   are hunting ([B4](../plans/max-locale-findings.md#c6-an-always-on-overlay-covers-a-static-sibling)
   was suppressed by that heuristic on the first pass). Tag same-layer
   collisions and overlay-covers-content ones separately and read both.

Run the same scan on `?ui-language=en` first and diff: it separates
Max-induced breakage from pre-existing layout debt.
